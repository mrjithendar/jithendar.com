This site, jithendar.com, is a Next.js application written in TypeScript: the pages, the comment box under this article, the admin editor and the API routes are all `.ts` and `.tsx` files. This tutorial uses that code to teach TypeScript from the beginning, ending with one feature, posting a comment, traced from the browser to the database.

You need everyday JavaScript (variables, functions, objects, arrays, `async`/`await`) and a rough idea of what React does. Each section starts with a small example, shows the same idea in the project, and names the mistake TypeScript catches. Everything was checked against the `www/` folder of the [jithendar.com repository](https://github.com/mrjithendar/jithendar.com/tree/dc249e807f83ef5a0e2aaa34638c42399e91e905/www) at commit `dc249e8` (TypeScript 6.0.3, Next.js 16.4.3, React 19.3.1, Zod 4.6.7). Blocks are labelled **Actual project code** (unchanged), **Simplified from project code** (what was left out is named) or **Standalone teaching example** (compiled with the project's TypeScript version and strictness). Examples meant to fail show the compiler's real error in a comment.

## What TypeScript is, and what it is not

TypeScript is JavaScript with type annotations. A **type** describes what a value may hold, and the **TypeScript compiler** (`tsc`) reports places where values do not match their types. This JavaScript has a mistake nothing warns you about:

*Standalone teaching example.*

```js
function readingTime(post, wordsPerMinute = 200) {
  const minutes = Math.max(1, Math.round(post.words / wordsPerMinute));
  return `${minutes} min read`;
}

readingTime({ title: "Hello", wordz: 1800 }); // typo: "wordz"
// Returns "NaN min read" instead of failing: post.words is undefined, so the maths gives NaN.
```

The same function in TypeScript:

*Standalone teaching example.*

```ts
type Post = { title: string; words: number };

function readingTime(post: Post, wordsPerMinute: number = 200): string {
  const minutes = Math.max(1, Math.round(post.words / wordsPerMinute));
  return `${minutes} min read`;
}

console.log(readingTime({ title: "Hello", words: 1800 }));
```

`type Post = ...` names an object's shape, `post: Post` and `wordsPerMinute: number` are **parameter annotations**, and `): string` is the **return type**. Now `wordz` instead of `words` is stopped before the code runs.

Browsers and Node.js run JavaScript, so a tool removes the types first. This is what `tsc` produces from the example above:

*Standalone teaching example.* (This is the compiler's output for the previous example, not code you write.)

```js
"use strict";
function readingTime(post, wordsPerMinute = 200) {
    const minutes = Math.max(1, Math.round(post.words / wordsPerMinute));
    return `${minutes} min read`;
}
console.log(readingTime({ title: "Hello", words: 1800 }));
```

The logic is identical and every annotation is gone: **types exist only while you write and check the code; at runtime it is plain JavaScript.** In this project, `npm run typecheck` (`next typegen && tsc --noEmit`) checks without writing files, and `next build` also fails on type errors. Next.js compiles with SWC, which strips types without checking them.

So TypeScript knows nothing about values that arrive while the program runs: JSON from `fetch`, form input, database rows, environment variables, or requests from someone not using your front end. Those need **runtime validation**, covered in the sections on API requests and `unknown`.

## Understanding .ts and .tsx files

React components describe their output with **JSX**, HTML-like tags inside JavaScript, which a compiler turns into ordinary function calls:

*Standalone teaching example.*

```js
function Greeting({ name }) {
  return <p>Hello, {name}</p>;
}
```

`.ts` files hold TypeScript without JSX (utilities, types, server logic); `.tsx` files hold TypeScript with JSX (components and pages). The compiler reads JSX only in `.tsx`, because TypeScript's older `<Type>value` assertion would look like a tag. JSX in a `.ts` file gives confusing errors; this is the first one TypeScript 6.0.3 reports:

*Standalone teaching example.* (Saved as `hello.ts`, deliberately the wrong extension.)

```ts
export const Hello = () => <p>Hello</p>;
// error TS1161: Unterminated regular expression literal.
```

Without JSX enabled, `/p>` looks like the start of a regular expression. Renaming the file to `hello.tsx` fixes it.

`www/src` has 179 `.ts` and 168 `.tsx` files. The shared comment types have no JSX:

*Actual project code from [`www/src/lib/comment-types.ts`](https://github.com/mrjithendar/jithendar.com/blob/dc249e807f83ef5a0e2aaa34638c42399e91e905/www/src/lib/comment-types.ts).*

```ts

export type Viewer = { id: string; role: "admin" | "author" | "user" } | null;

export type DiscussionState = { enabled: boolean; locked: boolean; requireApproval: boolean; editWindowMinutes: number };
```

The component that renders comments returns JSX:

*Actual project code from [`www/src/components/Comments.tsx`](https://github.com/mrjithendar/jithendar.com/blob/dc249e807f83ef5a0e2aaa34638c42399e91e905/www/src/components/Comments.tsx).*

## Basic types and type inference

The basic types are JavaScript's, in lower case:

*Standalone teaching example.*

```ts
const title = "Learning TypeScript";      // inferred: string
const readingMinutes = 12;                // inferred: number
const published = false;                  // inferred: boolean
const tags = ["typescript", "react"];     // inferred: string[]

const post: { title: string; minutes: number; tags: string[] } = {
  title,
  minutes: readingMinutes,
  tags,
};

let excerpt: string | null = null;        // nothing yet
excerpt = "A beginner-friendly tour.";
console.log(post, published, excerpt);
```

The first four lines have no annotations: TypeScript works the type out from the value (**type inference**). `string[]` is an array of strings, and the `post` line writes an **object type** inline.

Write annotations for **function parameters** (TypeScript cannot guess what callers pass), for **values that start empty and are filled in where TypeScript cannot follow**, such as object fields or React state (in `const draft = { subtitle: null }` the field's type is just `null`), and for **contracts** such as public return types, so a wrong return is reported in the function, not in every caller. Skip `const count: number = 0`; it adds nothing.

### null, undefined and unions

`undefined` usually means "never set" and `null` "deliberately empty". In strict mode, which this project uses, neither is allowed unless the type says so. `|` creates a **union type**, "one of these", and TypeScript makes you handle `null` before using string features:

*Standalone teaching example.*

```ts
function excerptLength(excerpt: string | null): number {
  return excerpt.length;
}
// error TS18047: 'excerpt' is possibly 'null'.
```

After a check, TypeScript knows the value is a string:

*Standalone teaching example.*

```ts
function excerptLength(excerpt: string | null): number {
  if (excerpt === null) return 0;
  return excerpt.length;
}
```

The project also turns on `noUncheckedIndexedAccess`, so `items[0]` is "the item type, or `undefined`", because arrays can be empty:

*Standalone teaching example.*

```ts
const tags = ["typescript", "react"];
console.log(tags[0].toUpperCase());
// error TS2532: Object is possibly 'undefined'.
```

`?.` (**optional chaining**) returns `undefined` when the left side is missing, and `??` (**nullish coalescing**) supplies a fallback for `null` or `undefined`:

*Standalone teaching example.*

```ts
const tags = ["typescript", "react"];
console.log(tags[0]?.toUpperCase() ?? "no tags");
```

The project uses that pattern when there may be no comment thread:

*Actual project code from [`www/src/app/_actions/comments.ts`](https://github.com/mrjithendar/jithendar.com/blob/dc249e807f83ef5a0e2aaa34638c42399e91e905/www/src/app/_actions/comments.ts).*

```ts
/** The thread containing `id`, as this user sees it (after posting, editing or deleting). */
async function threadOf(postId: string, id: string, user: SessionUser): Promise<CommentView | null> {
  const page = await listComments(postId, { id: user.id, role: user.role }, { focus: id });
  return page.threads[0] ?? null;
}
```

`page.threads[0]` alone is "a thread, or `undefined`", so `?? null` converts it to the `null` the return type promises. **What TypeScript catches:** code that assumes a value is present. "Cannot read properties of undefined" is one of the most common JavaScript runtime errors, and these checks move many of them to compile time.

**Try it:** write `const draft = { title: "Hello", subtitle: null };` then `draft.subtitle = "World";`, read the error (`TS2322: Type '"World"' is not assignable to type 'null'`), and fix it by annotating `subtitle` as `string | null`.

## Functions

A function's types are its parameters and its return value. A JavaScript slug helper:

*Standalone teaching example.*

```js
function tagSlug(tag) {
  return tag.toLowerCase().trim().replace(/\s+/g, "-");
}

tagSlug(42); // TypeError at runtime: tag.toLowerCase is not a function
```

The project's version says what it accepts and returns:

*Actual project code from [`www/src/config/taxonomy.ts`](https://github.com/mrjithendar/jithendar.com/blob/dc249e807f83ef5a0e2aaa34638c42399e91e905/www/src/config/taxonomy.ts).*

```ts
/** URL-safe slug for a tag ("Argo CD" → "argo-cd"). */
export function tagSlug(tag: string): string {
  return tag
    .toLowerCase()
    .normalize("NFKD")
    .replace(/[^\w\s-]/g, "")
    .trim()
    .replace(/[\s_]+/g, "-")
    .replace(/-+/g, "-");
}
```

`tag: string` rejects `tagSlug(42)`, and `: string` lets every caller use string methods on the result without checking.

*Standalone teaching example.*

```ts
function readingTime(words: number, wordsPerMinute: number = 200): string {
  const minutes = Math.max(1, Math.round(words / wordsPerMinute));
  return `${minutes} min read`;
}
readingTime(1800);       // "9 min read"
readingTime(1800, 300);  // "6 min read"

function greet(name?: string): string {
  return `Hello, ${name ?? "reader"}`;
}
greet();
greet("Asha");

const double = (n: number): number => n * 2;
double(4);
```

`wordsPerMinute: number = 200` is a **default value** (the type could be inferred from it), and `name?: string` an **optional parameter** whose type inside is `string | undefined`. Arrow functions take annotations the same way. The sign-in redirect helper combines a union parameter and a default:

*Actual project code from [`www/src/lib/safe-next.ts`](https://github.com/mrjithendar/jithendar.com/blob/dc249e807f83ef5a0e2aaa34638c42399e91e905/www/src/lib/safe-next.ts).*

```ts
export function safeNext(next: string | null | undefined, fallback = "/account"): string {
```

That is only the first line. The value comes from a URL query parameter, which may be missing, hence `string | null | undefined`. The body (not shown) rejects anything that is not a same-site path at runtime, because a string type says nothing about whether a string is a safe address. A second helper calls it:

*Actual project code from [`www/src/lib/safe-next.ts`](https://github.com/mrjithendar/jithendar.com/blob/dc249e807f83ef5a0e2aaa34638c42399e91e905/www/src/lib/safe-next.ts).*

```ts
/** The sign-in URL that returns to `path` afterwards. */

  const next = safeNext(path, "");
  return next && next !== "/" ? `/login?next=${encodeURIComponent(next)}` : "/login";
}
```

**What TypeScript catches:** calls with the wrong kind of value.

*Standalone teaching example.*

```ts
function readingTime(words: number, wordsPerMinute: number = 200): string {
  return `${Math.max(1, Math.round(words / wordsPerMinute))} min read`;
}
readingTime("1800");
// error TS2345: Argument of type 'string' is not assignable to parameter of type 'number'.
```

In JavaScript `"1800" / 200` happens to work through automatic conversion, which is why this bug survives until it does not. **Try it:** write `formatTags(tags: string[], separator = ", "): string` and call it with and without the second argument.

## Describing objects with type and interface

*Standalone teaching example.*

```ts
type Author = {
  name: string;
  image: string | null;     // always present, may be empty
  website?: string;         // may be missing entirely
};

interface Comment {
  readonly id: string;
  body: string;
  author: Author;
}

const c: Comment = { id: "c1", body: "Nice post", author: { name: "Asha", image: null } };
c.body = "Edited";
console.log(c.author.website?.length);
```

A **type alias** names any type; an **interface** names an object shape only. `website?: string` is an **optional property** (the field may be absent), unlike `image: string | null` (always present, maybe `null`). `readonly` forbids reassignment after creation.

For object shapes the two behave almost the same. Only `type` can name a union; interfaces extend with `extends` where types use `&`; and declaring an interface twice merges the two, while a duplicate `type` is an error. Pick one style per project. jithendar.com uses `type`, and at `dc249e8` has exactly two `interface` declarations, both using merging to add a field to the browser's built-in `Window`:

*Actual project code from [`www/src/components/Turnstile.tsx`](https://github.com/mrjithendar/jithendar.com/blob/dc249e807f83ef5a0e2aaa34638c42399e91e905/www/src/components/Turnstile.tsx).*

```tsx
declare global {
  interface Window {
    turnstile?: {
      render: (el: HTMLElement, opts: Record<string, unknown>) => string;
      reset: (id?: string) => void;
      remove: (id: string) => void;
    };
  }
}
```

This adds an optional `turnstile` field describing what Cloudflare's Turnstile script creates (the human check on the sign-in and contact forms), so `window.turnstile?.reset()` type-checks everywhere. A `type` alias cannot be reopened like this.

The stored data shapes are plain `type` aliases, such as a post's cover image in a JSON column, where missing `focalX?` and `focalY?` mean "centred":

*Actual project code from [`www/src/db/schema.ts`](https://github.com/mrjithendar/jithendar.com/blob/dc249e807f83ef5a0e2aaa34638c42399e91e905/www/src/db/schema.ts).*

```ts

```

*Simplified from project code in [`www/src/lib/post-form.ts`](https://github.com/mrjithendar/jithendar.com/blob/dc249e807f83ef5a0e2aaa34638c42399e91e905/www/src/lib/post-form.ts). Omitted: 20 of the 25 fields.*

## Union types and narrowing

A **literal type** is one exact value, such as `"draft"`, and a union of literals lists every allowed option:

*Standalone teaching example.*

```ts
type Status = "draft" | "review" | "published";

function badgeLabel(status: Status): string {
  if (status === "published") return "Live";
  return "Not public yet";
}
badgeLabel("review");
```

In JavaScript a typo in a status would fall through to the wrong branch. Here it is caught:

*Standalone teaching example.*

```ts
type Status = "draft" | "review" | "published";
const s: Status = "pubished";
// error TS2820: Type '"pubished"' is not assignable to type 'Status'. Did you mean '"published"'?
```

You have seen this already: `CommentSort` is `"oldest" | "newest"`. The project also builds a union from a runtime list, so the list and the type cannot drift apart:

*Actual project code from [`www/src/lib/comment-types.ts`](https://github.com/mrjithendar/jithendar.com/blob/dc249e807f83ef5a0e2aaa34638c42399e91e905/www/src/lib/comment-types.ts).*

```ts
export const REPORT_REASONS = ["spam", "abuse", "off-topic", "other"] as const;
export type ReportReason = (typeof REPORT_REASONS)[number];
export const reportReasonLabels: Record<ReportReason, string> = {
  spam: "Spam or advertising",
  abuse: "Harassment, hate or abuse",
  "off-topic": "Off-topic",
  other: "Something else",
};
```

`as const` keeps the exact strings instead of widening to `string[]`. `typeof REPORT_REASONS` asks for the array's type and `[number]` for any element of it, giving `"spam" | "abuse" | "off-topic" | "other"`. `Record<ReportReason, string>` needs exactly those four keys, so a fifth reason without a label stops compiling. You can use this pattern long before you write it.

When a value can be several types, you **narrow** it with a check, and TypeScript updates the type in that branch. `typeof`, `===` against literals, `instanceof` and `Array.isArray` all narrow:

*Standalone teaching example.*

```ts
function formatId(id: string | number): string {
  if (typeof id === "number") return id.toFixed(0);
  return id.trim();
}
formatId(42);
```

A **discriminated union** is a union of object types sharing one field (the **discriminant**) with a different literal in each:

*Standalone teaching example.*

```ts
type SaveResult = { ok: true; id: string } | { ok: false; error: string };

function describe(result: SaveResult): string {
  if (result.ok) return `Saved as ${result.id}`;
  return `Failed: ${result.error}`;
}
describe({ ok: false, error: "Too long" });
```

Reading `result.error` before checking `ok` is an error:

*Standalone teaching example.*

```ts
type SaveResult = { ok: true; id: string } | { ok: false; error: string };
function describe(result: SaveResult): string {
  return result.error;
}
// error TS2339: Property 'error' does not exist on type 'SaveResult'.
//   Property 'error' does not exist on type '{ ok: true; id: string; }'.
```

The comment composer uses exactly this shape for what runs when you press **Post**:

*Actual project code from [`www/src/components/discussion/Composer.tsx`](https://github.com/mrjithendar/jithendar.com/blob/dc249e807f83ef5a0e2aaa34638c42399e91e905/www/src/components/discussion/Composer.tsx).*

```ts
export type ComposerSubmit = (body: string, clientKey: string) => Promise<{ ok: true } | { ok: false; error: string }>;
```

That is a **function type**: two strings in, a promise of a result out (the arrow separates parameters from the return type here). The composer checks `ok` before it reads `error`:

*Actual project code from [`www/src/components/discussion/Composer.tsx`](https://github.com/mrjithendar/jithendar.com/blob/dc249e807f83ef5a0e2aaa34638c42399e91e905/www/src/components/discussion/Composer.tsx).*

```tsx
      const r = await onSubmit(body, clientKey.current);
      if (!r.ok) {
        setError(r.error);
        return;
      }
```

**What TypeScript catches:** fields that exist in only one case, and misspelt options. **Try it:** add `"archived"` to `Status` in `badgeLabel` and notice nothing breaks, because of the catch-all `return`; the answers show how to make TypeScript list every place to update.

## TypeScript in React components

Almost half the site's TypeScript files are `.tsx`. React components are functions that return JSX, and **hooks** are `use...` functions: `useState` stores a value and re-renders when it changes, `useRef` holds a value (often a DOM element) without re-rendering, and `useTransition` shows a pending state during an update.

**Props**, a component's inputs, are typed like any function parameter:

*Standalone teaching example.*

```tsx
type GreetingProps = {
  name: string;
  excited?: boolean;
};

export function Greeting({ name, excited = false }: GreetingProps) {
  return <p>Hello, {name}{excited ? "!" : "."}</p>;
}

export function Usage() {
  return <><Greeting name="Asha" /><Greeting name="Ravi" excited /></>;
}
```

The braces **destructure** `name` and `excited` from the props, and `excited = false` makes that prop optional. The real composer types its props inline:

*Actual project code from [`www/src/components/discussion/Composer.tsx`](https://github.com/mrjithendar/jithendar.com/blob/dc249e807f83ef5a0e2aaa34638c42399e91e905/www/src/components/discussion/Composer.tsx).*

```tsx
export function Composer({
  label,
  submitLabel,
  pendingLabel = "Posting…",
  initial = "",
  autoFocus = false,
  onSubmit,
  onCancel,
}: {
  label: string;
  submitLabel: string;
  pendingLabel?: string;
  initial?: string;
  autoFocus?: boolean;
  onSubmit: ComposerSubmit;
  onCancel?: () => void;

```

It serves new comments, replies and edits. `onSubmit` must match `ComposerSubmit`; `onCancel?: () => void` is optional ("takes nothing, return value ignored"), and the **Cancel** button appears only when it is passed. Leaving out a required prop is caught where you use the component:

*Standalone teaching example.*

```tsx
function Greeting({ name }: { name: string }) { return <p>{name}</p>; }
export const x = <Greeting />;
// error TS2741: Property 'name' is missing in type '{}' but required in type '{ name: string; }'.
```

### Typed state

The composer's state:

*Actual project code from [`www/src/components/discussion/Composer.tsx`](https://github.com/mrjithendar/jithendar.com/blob/dc249e807f83ef5a0e2aaa34638c42399e91e905/www/src/components/discussion/Composer.tsx).*

```tsx
  const id = useId();
  const [body, setBody] = useState(initial);
  const [tab, setTab] = useState<"write" | "preview">("write");
  const [preview, setPreview] = useState<{ html?: string; error?: string; loading?: boolean }>({});
  const [error, setError] = useState<string | null>(null);
  const [pending, start] = useTransition();
  const clientKey = useRef(newKey());
  const textarea = useRef<HTMLTextAreaElement>(null);
```

`useState(initial)` infers `string`. `useState<"write" | "preview">("write")` passes a type in angle brackets, without which `setTab("wirte")` would be allowed (a generic, covered later). `useState<string | null>(null)` is the **nullable state** pattern, "no error yet, a message later". `useRef<HTMLTextAreaElement>(null)` points at a textarea once React attaches it, which is why the code writes `textarea.current?.focus()`. Without the type, nullable state can only ever be `null`:

*Standalone teaching example.*

```tsx
import { useState } from "react";
export function F() {
  const [error, setError] = useState(null);
  setError("Too long");
  return <p>{error}</p>;
}
// error TS2345: Argument of type '"Too long"' is not assignable to parameter of type 'SetStateAction<null>'.
```

## API requests and asynchronous code

An `async` function returns a **promise**, written `Promise<T>` where `T` is the type it will hold:

### Declaring a type is not checking the data

`res.json()` returns `Promise<any>`, because TypeScript cannot know what a server sends. `as CommentPage` is a **type assertion**: "trust me". Nothing is checked at runtime. This script type-checks without errors:

*Standalone teaching example.*

```ts
type Post = { slug: string; title: string };
const json = '{"slug": "hello", "headline": "Hello"}'; // the server renamed a field
const post = JSON.parse(json) as Post;                  // TypeScript is satisfied
console.log(post.title);                                // undefined at runtime
console.log(post.title.toUpperCase());                  // TypeError at runtime
```

Run with Node.js 26, the first `console.log` prints `undefined` and the second throws `TypeError: Cannot read properties of undefined (reading 'toUpperCase')`, although the type says `title` is a string. In `fetchPage` the assertion is a reasonable trade-off, since the browser calls a same-codebase route whose response is type-checked on the server, but the two sides can drift apart if one changes and the other is not rebuilt.

### Runtime validation with Zod

For data you do not control, the project validates at runtime with **Zod**: you describe the shape as a **schema**, and Zod checks the value and gives you correctly typed data. The Python practice route that saves a learner's draft, note or bookmark:

*Actual project code from [`www/src/app/api/practice/problems/[slug]/state/route.ts`](https://github.com/mrjithendar/jithendar.com/blob/dc249e807f83ef5a0e2aaa34638c42399e91e905/www/src/app/api/practice/problems/%5Bslug%5D/state/route.ts).*

```ts

/** PUT { draft } | { note } | { bookmarked }. */
export async function PUT(req: Request, { params }: { params: Promise<{ slug: string }> }) {

  return withUser(
    req,
```

## any, unknown and safe error handling

`any` switches checking off, and it spreads: everything derived from an `any` value is `any` too.

*Standalone teaching example.*

```ts
const data: any = JSON.parse('{"title": "Hello"}');
data.title.toUpperCase();  // fine
data.tilte.toUpperCase();  // also "fine" to the compiler; crashes at runtime
```

Strict mode refuses to assume `any` silently, so an untyped parameter is an error:

*Standalone teaching example.*

```ts
export function double(n) { return n * 2; }
// error TS7006: Parameter 'n' implicitly has an 'any' type.
```

At `dc249e8`, `www/src` has no `any` annotations, no `as any` and no `@ts-ignore`. `unknown` is the safe opposite: anything can be assigned to it, but you cannot use it until you narrow it:

*Standalone teaching example.*

```ts
function lengthOf(value: unknown): number {
  if (typeof value === "string") return value.length;
  if (Array.isArray(value)) return value.length;
  return 0;
}
lengthOf("hi");
```

That is the right type for outside values. The comment system takes a new comment's text as `unknown`, although browsers normally send a string, and checks it:

*Actual project code from [`www/src/lib/comments.ts`](https://github.com/mrjithendar/jithendar.com/blob/dc249e807f83ef5a0e2aaa34638c42399e91e905/www/src/lib/comments.ts).*


*Actual project code from [`www/src/lib/post-form.ts`](https://github.com/mrjithendar/jithendar.com/blob/dc249e807f83ef5a0e2aaa34638c42399e91e905/www/src/lib/post-form.ts).*

## Generics

A **generic** is a type with a blank, a **type parameter** in angle brackets (usually `T`) that TypeScript fills in at each use:

*Standalone teaching example.*

```ts
function firstOr<T>(items: T[], fallback: T): T {
  return items[0] ?? fallback;
}
const n = firstOr([3, 5, 8], 0);        // T is number
const s = firstOr(["a", "b"], "none");  // T is string
console.log(n.toFixed(1), s.toUpperCase());
```

Read it as "for some type T, take an array of T and a fallback T, and return a T". TypeScript infers `T` from the arguments; without generics you would need one function per type, or `any`. You have already used generics: `Promise<CommentPage>`, `useState<string | null>(null)`, and `Record<K, V>`, an object with keys `K` and values `V`:

```ts

```

*Actual project code from [`www/src/components/practice/api.ts`](https://github.com/mrjithendar/jithendar.com/blob/dc249e807f83ef5a0e2aaa34638c42399e91e905/www/src/components/practice/api.ts).*

```ts
export async function api<T>(path: string, init: { method?: string; body?: unknown; signal?: AbortSignal } = {}): Promise<T> {
  const res = await fetch(path, {
    method: init.method ?? (init.body === undefined ? "GET" : "POST"),
    headers: init.body === undefined ? undefined : { "Content-Type": "application/json" },
    body: init.body === undefined ? undefined : JSON.stringify(init.body),
    signal: init.signal,
    credentials: "same-origin",
    cache: "no-store",
  });
  const data = (await res.json().catch(() => ({}))) as { error?: string; code?: string };
  if (!res.ok) throw new ApiError(data.error ?? `Request failed (${res.status}).`, res.status, data.code ?? "error", Number(res.headers.get("retry-after")) || undefined);
  return data as T;
}
```

A caller writes `api<{ ok: true }>("/api/...")` and gets that type. Note `return data as T`: as with `fetchPage`, nothing checks that the server sent a `T`. The comment actions share a generic result type:

*Actual project code from [`www/src/app/_actions/comments.ts`](https://github.com/mrjithendar/jithendar.com/blob/dc249e807f83ef5a0e2aaa34638c42399e91e905/www/src/app/_actions/comments.ts).*

```ts

```

`T = object` is a **default type parameter**, and `& T` merges the success fields with each action's extra data, such as a like action's `likes` and `liked`. The wrapper is `async function signedIn<T extends object>(...)`, where `T extends object` is a **constraint**: any object type, but not a string or number, because the code spreads it into an object.

| Option | What it does here | TypeScript 6.0.3 default if left out |
|---|---|---|
| `strict: true` | Turns on the whole family of strict checks, including null checks and no implicit `any` | `true` (older versions defaulted to `false`) |
| `noUncheckedIndexedAccess: true` | `items[0]` may be `undefined` | `false`, so this one makes the project stricter than the default |
| `noEmit: true` | Check only. Next.js does the actual compiling | `false` |
| `target: "ES2022"` | Which JavaScript version the type checker assumes | `es2025` |
| `lib` | Which built-in APIs exist: browser DOM plus the latest JavaScript | Based on `target` |
| `jsx: "react-jsx"` | How JSX in `.tsx` files is understood | Not set |
| `module` and `moduleResolution` | `esnext` and `bundler`: modern `import`/`export`, resolved the way a bundler resolves them | `bundler` resolution unless `module` is a Node mode |
| `isolatedModules: true` | Every file must be compilable on its own, because SWC compiles one file at a time | `false` |
| `esModuleInterop: true` | Smooths importing older CommonJS packages | `true` |
| `skipLibCheck: true` | Does not type-check the `.d.ts` files inside installed packages, which is faster | `false` |
| `allowJs: false` | Only TypeScript files are part of the program | `false` |
| `resolveJsonModule: true` | Allows `import data from "./file.json"` | `false` |
| `incremental: true` | Caches results between runs in `tsconfig.tsbuildinfo` | `false` |
| `plugins: next` | Loads the Next.js plugin for editor hints | None |
| `paths` | The `@/` import alias, explained below | None |

`strict` bundles the checks you met here: **`strictNullChecks`** (the "possibly null" errors), **`noImplicitAny`** (untyped parameters are errors) and **`useUnknownInCatchVariables`** (`catch (error)` is `unknown`). Keep it on from the first day; switching it on later means fixing every error at once.

```ts
      status: r.status,
      thread: await threadOf(input.postId, r.id, user),
      message: r.status === "approved" ? "Your comment is published." : "Thanks! Your comment will appear after a moderator approves it.",
    };
  });
}
```

There is no return annotation: TypeScript infers it from `signedIn`, and step 2 relies on that inferred type. The user comes "from the session cookie (never from the arguments)".

**Step 4: the business logic checks everything again at runtime.** A server action is still an HTTP endpoint that anyone can call with a hand-made request, so `submitComment` treats its input as untrusted:

*Simplified from project code in [`www/src/lib/comments.ts`](https://github.com/mrjithendar/jithendar.com/blob/dc249e807f83ef5a0e2aaa34638c42399e91e905/www/src/lib/comments.ts). Omitted: the duplicate-submission lookup, the parent-comment checks, the rate limit and duplicate-text queries, and the race-condition retry.*

```ts
export type SubmitInput = { postId: string; parentId?: string | null; body: unknown; clientKey?: string | null };

export async function submitComment(user: { id: string; role: string }, input: SubmitInput): Promise<{ id: string; status: "approved" | "pending"; duplicate: boolean }> {
  const state = await discussionFor(input.postId);
  assertOpen(state);
  const text = cleanBody(input.body);
  const clientKey = input.clientKey && CLIENT_KEY.test(input.clientKey) ? input.clientKey : null;
  // ...
  const staff = user.role === "admin" || user.role === "author";
  const status = staff || !state.requireApproval ? "approved" : "pending";
  // ...
}
```

`cleanBody()` rejects a missing, non-string, too-short or too-long `body: unknown`. `discussionFor(input.postId)` starts with an `isUuid` check, then confirms the post exists, is published and is not deleted, and `assertOpen(state)` rejects closed or locked discussions. The client key must match `/^[A-Za-z0-9_-]{8,64}$/` or is ignored, and the status comes from the user's role on the server. The `Promise<{ id: string; status: "approved" | "pending"; duplicate: boolean }>` return type makes every `return` in this long function produce the same shape.

**Step 5: the database.** The insert goes through Drizzle, which describes tables in TypeScript:

*Simplified from project code in [`www/src/db/schema.ts`](https://github.com/mrjithendar/jithendar.com/blob/dc249e807f83ef5a0e2aaa34638c42399e91e905/www/src/db/schema.ts). Omitted: the moderation, depth and timestamp columns, and the indexes and foreign keys.*

```ts
export const comment = pgTable(
  "comment",
  {
    id: uuid("id").primaryKey().defaultRandom(),
    postId: uuid("post_id")
      .notNull()
      .references(() => post.id, { onDelete: "cascade" }),
    // ...
    body: text("body").notNull(),
    status: text("status").notNull().default("pending"),
    // ...
    parentId: uuid("parent_id"),
    // ...
    clientKey: text("client_key"),
  },
  // ...
);
```

`.notNull()` columns become `string` and the rest, like `parentId`, `string | null`, so an insert missing `body` will not compile. One gap: `status` is a `text` column, so TypeScript sees any `string`, which is why `submitComment` converts it back with `first.status === "approved" ? "approved" : "pending"`. The database adds rules no type can see: a unique index on user and client key, and a foreign key keeping a reply on its parent's post.

**Step 6: back to the browser.** The result returns as a `CommentResult`; on failure `signedIn` returns `{ ok: false, error }`, plus `signedOut: true` when the session has ended, and the discussion shows a sign-in prompt.

| Concern | Checked by |
|---|---|
| The client passes the fields the server action expects | TypeScript, at compile time |
| The client reads `id` and `status` only on success | TypeScript (discriminated union) |
| Every return in `submitComment` has the same shape | TypeScript |
| A required database column is not forgotten | TypeScript, through Drizzle's types |
| The request really contains a string body of the right length | Runtime: `cleanBody` |
| The post id is a real, open, published post | Runtime: `isUuid` and a database query |
| The user is signed in, and who they are | Runtime: the session cookie |
| No duplicate comment from a double click | Runtime: client key and a unique index |
| A reply is on the same post as its parent | Runtime: code check and a database foreign key |

The top half helps the people writing the code; the bottom half protects the site from its users. You need both.

## Common beginner mistakes

- **JSX in a .ts file** gives unrelated-looking errors such as `TS1161: Unterminated regular expression literal`. Rename to `.tsx`.
- **Reaching for `any`** switches checking off for that value and everything derived from it. Use `unknown` and narrow, or describe the real type.
- **Using `as` to silence an error** hides the mismatch until runtime. Use assertions only when a check backs them, as `includes` does in `reportComment`.
- **Trusting API JSON because it has a type.** `(await res.json()) as CommentPage` documents, it does not check. Validate outside data with a schema.
- **Ignoring `TS18047: 'x' is possibly 'null'` or `TS2532: Object is possibly 'undefined'`.** Handle the case with `if`, `?.` or `??`; use `!` only when you can say why the value must exist.
- **Untyped nullable state.** `useState(null)` can only ever hold `null` (`TS2345 ... SetStateAction<null>`); write `useState<string | null>(null)`.
- **Annotating everything.** `const title: string = "Hello"` repeats inference. Annotate parameters, empty starting values and public return types.
- **`TS2820 ... Did you mean '"published"'?`** is your literal union catching a typo; accept the suggestion. **`TS2339: Property 'error' does not exist on type ...`** on a discriminated union means check the discriminant first.

## Practice exercises

Use a `.ts` or `.tsx` file with `strict` on; the compiler tells you whether you got it right.

1. **Functions.** Write `formatTags` taking an array of strings and an optional separator defaulting to `", "`. `formatTags(["a", "b"])` returns `"a, b"`.
2. **Literal unions.** Define `DiscussionMode` as `"open"`, `"locked"` or `"closed"`, and `canPost(mode)` true only for `"open"`. Check that `canPost("opne")` fails to compile.
3. **Nullable React state.** Fix this component without `any`:

*Standalone teaching example.* (Deliberately broken.)

```tsx
import { useState } from "react";
export function SaveButton() {
  const [message, setMessage] = useState(null);
  return <button onClick={() => setMessage("Saved")}>{message ?? "Save"}</button>;
}
// error TS2345: Argument of type '"Saved"' is not assignable to parameter of type 'SetStateAction<null>'.
```

4. **unknown and catch.** Write `safeJsonTitle(text: string): string` that returns the JSON's `title` if it is a string, or `"Untitled"` otherwise, including for invalid JSON, with no `any` and no `as`.
5. **Generics.** Write `lastOr` returning an array's last item or a fallback; `lastOr([1, 2, 3], 0)` has type `number`.

## Suggested answers

Each compiles with the project's settings.

**1. Functions**

*Standalone teaching example.*

```ts
function formatTags(tags: string[], separator = ", "): string {
  return tags.join(separator);
}
formatTags(["a", "b"]);        // "a, b"
formatTags(["a", "b"], " / "); // "a / b"
```

**2. Literal unions**, plus the exhaustive check promised earlier:

*Standalone teaching example.*

```ts
type DiscussionMode = "open" | "locked" | "closed";

function canPost(mode: DiscussionMode): boolean {
  return mode === "open";
}

function modeLabel(mode: DiscussionMode): string {
  switch (mode) {
    case "open": return "Open";
    case "locked": return "Locked";
    case "closed": return "Closed";
    default: {
      const unhandled: never = mode; // fails to compile if a new mode is not handled above
      return unhandled;
    }
  }
}
canPost("open");
modeLabel("locked");
```

`never` has no possible values. Once every case is handled nothing is left for `mode`, so assigning it to `never` compiles; add `"archived"` and the line fails with `TS2322: Type '"archived"' is not assignable to type 'never'.`, pointing at the missing case. The project's runtime list is `DISCUSSION_MODES = ["open", "locked", "closed"] as const` in `www/src/lib/comments.ts`.

**3. Nullable React state**

*Standalone teaching example.*

```tsx
import { useState } from "react";
export function SaveButton() {
  const [message, setMessage] = useState<string | null>(null);
  return <button onClick={() => setMessage("Saved")}>{message ?? "Save"}</button>;
}
```

**4. unknown and catch**

*Standalone teaching example.*

```ts
function safeJsonTitle(text: string): string {
  let data: unknown;
  try {
    data = JSON.parse(text);
  } catch {
    return "Untitled";
  }
  if (typeof data === "object" && data !== null && "title" in data && typeof data.title === "string") {
    return data.title;
  }
  return "Untitled";
}
safeJsonTitle('{"title": "Hello"}'); // "Hello"
safeJsonTitle("not json");           // "Untitled"
```

`JSON.parse` returns `any`, so storing it in an `unknown` variable puts the checks back. `catch` without a variable is allowed, and `data !== null` matters because `typeof null` is `"object"`.

**5. Generics**

*Standalone teaching example.*

```ts
function lastOr<T>(items: T[], fallback: T): T {
  return items.at(-1) ?? fallback;
}
const n = lastOr([1, 2, 3], 0);      // number
const s = lastOr<string>([], "none"); // string, written explicitly because [] alone says nothing
console.log(n, s);
```
