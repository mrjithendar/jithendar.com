Microservices are easy to draw and expensive to run. [RoboShop AI](/projects/roboshop-ai) is a robot store I built as a learning project, split into separately deployed services on purpose, because practising distributed operations is the point. That makes it a useful case study. The boundaries are real, the costs are visible, and for a shop this size a monolith would clearly be simpler.

This article follows three kinds of request through the system: a product page, an AI chat turn and a paid order. It then looks at what each boundary buys, what it costs, and what I would do differently for a real business. It is a demo with test-mode payments and no customers, so where something is an architectural possibility rather than something demonstrated, I say so.

## Where it runs

:::callout{type="info" title="Checked on 2026-11-01"}
The shop runs on a two-node Amazon EKS cluster at [eks.jithendar.com/roboshop](https://eks.jithendar.com/roboshop/). It moved from a Minikube lab, whose RoboShop namespace is gone. Every application Deployment runs one replica. The Moks assistant is **not deployed** on this cluster, so chat fails while shopping works. Sidecars are in place, but mTLS is permissive and mesh policies are in dry run. The [deployment guide](/blog/deploy-roboshop-ai-amazon-eks) has the details.
:::

## From Robot Shop to RoboShop AI

RoboShop AI started from Instana's [Robot Shop](https://github.com/instana/robot-shop), a polyglot sample application for learning container orchestration and monitoring. Its catalogue, user, cart, shipping and payment boundaries survive, and the storefront still ships some original images under their Apache 2.0 licence.

Most of the implementations are new. Shipping keeps its Java design on Java 21, Spring Boot and PostgreSQL. The dummy payment service became a [Razorpay integration](https://github.com/mrjithendar/roboshop-ai/blob/c81e85a1fd9d3552c69d4490be17ccf61d29437b/services/payment-service/README.md). The AI gateway, the Moks agent, the MCP server, a currency service and a Kafka bridge were added.

The storefront itself is a catalogue of twenty robots with search, filters, product pages, a cart and checkout. Prices are labelled as demo prices, and product images are labelled as AI-generated concept renders.

## What makes a service boundary useful

A boundary earns its cost when it matches a capability that changes for its own reasons, owns its data, and is reached through a narrow contract. It works against you when two services must always change together, share tables, or call each other on every request.

Not every box in a diagram is a business microservice. The NLB, the Istio gateway and NGINX are edge. MongoDB, Redis and PostgreSQL are data stores. RabbitMQ and Kafka are brokers. Counting them as services inflates the architecture without adding business capability.

## How responsibilities are divided

:::figure{caption="Figure 1. What runs on EKS. One public path, ai-gateway as the API entry point, and each service's data store."}
![RoboShop AI on Amazon EKS. A browser reaches a Network Load Balancer, then the Istio ingress gateway, which ends TLS and strips /roboshop, then web. web sends API calls to ai-gateway, which calls user, catalogue, cart, payment, shipping and currency services. mcp-server is private. moks is marked as not deployed. Paid orders flow from the gateway outbox through RabbitMQ to shipping-service and kafka-bridge.](/images/roboshop-ai/roboshop-ai-eks-services.svg)
:::

| Service | Responsibility | Data and dependencies |
| --- | --- | --- |
| `web` (NGINX, TypeScript) | Static storefront and reverse proxy | Proxies `/api/*`, `/moks/*` and currency rates; holds no data |
| `ai-gateway` (Python) | Public API, sessions, admin roles, checkout, event outbox | MongoDB settings and chat history; JSON order ledger on a volume |
| `user-service` (Python) | Accounts, sessions, MFA, recovery, purchase history | MongoDB users; Amazon SES for email |
| `catalogue-service` (Node.js) | Product reads, search, recommendations, imports | MongoDB `products` |
| `cart-service` (Python) | Cart lines with compare-and-set revisions | Redis |
| `payment-service` (Node.js) | Razorpay orders, signature and capture checks | Razorpay API; no database |
| `shipping-service` (Java) | Locations, quotes, shipment requests | Own PostgreSQL; consumes RabbitMQ |
| `currency-service` (Go) | Display exchange rates | In-memory cache of the ECB feed |
| `moks` (Python, LangGraph) | Shopping assistant, optional | Catalogue, Bedrock or Ollama; no database credentials |
| `mcp-server` (Python, FastMCP) | MCP tools for search, compare and cart | Calls the gateway with the caller's session |
| `kafka-bridge` (Python) | Copies order events to Kafka | Container in the Kafka StatefulSet |

Data ownership isn't perfectly clean, and it's worth being honest about that. The MongoDB "stores" are collections in one instance with a shared application credential. catalogue-service reads `products`, while the gateway writes admin edits to the same collection. Ownership here is a convention held up by code paths, not by separate databases.

## How a product page request travels

A product page is a static file. The Istio gateway ends TLS, strips `/roboshop` and forwards the request to `web`, which serves generated HTML.

The page script then calls `/api/products`. NGINX proxies it to the gateway with no retries or buffering, and the gateway calls catalogue-service, which reads MongoDB.

Before responding, [the gateway](https://github.com/mrjithendar/roboshop-ai/blob/c81e85a1fd9d3552c69d4490be17ccf61d29437b/services/ai-gateway/server.py) recalculates `instock` from reservations and sales in its own ledger, because stock authority lives with checkout and not the catalogue. A simple product list therefore touches two services and a database.

Prices show a useful small boundary. `currency-service` downloads the European Central Bank feed hourly, with a five-second deadline and a 64 KiB limit. Requests only ever read the cache, so a slow upstream cannot slow the storefront. After two hours rates are labelled stale, and after seven days they are withdrawn rather than guessed. If the service is gone entirely, the browser shows original prices.

## How an AI chat turn differs

:::figure{caption="Figure 2. The code's design for the assistant and MCP, two independent entry points. Path A is not running on EKS today."}
![AI request paths. Path A: browser widget, web, Moks widget routes, ai-gateway /api/chat, Moks engine, which reads catalogue-service, confirms its configuration revision with the gateway and calls Bedrock or Ollama. Path B: MCP client, private mcp-server, ai-gateway, domain services. Moks does not call MCP.](/images/roboshop-ai/roboshop-ai-ai-paths.svg)
:::

A chat turn has more hops and much tighter limits than a product request. This describes the code, since Moks isn't running on EKS right now.

The widget posts to `/moks/chat`, and NGINX blocks browser calls to `/api/chat`. Moks's widget routes check the session and Origin, then call the gateway, which applies a rate limit and allows two concurrent chats. Extra requests get `429 assistant-busy`.

The gateway adds saved product references, the SKUs that cannot be shown and the active model configuration. It calls the Moks engine with a service token. The engine runs a short [LangGraph](https://langchain-ai.github.io/langgraph/) graph: `search_catalogue → ground_evidence → generate_answer`. Before the model call it confirms the configuration revision with the gateway, and only then does Amazon Bedrock or an approved Ollama endpoint generate an answer. A fresh install has no model connected.

Because model calls are slow and paid for, this path has explicit budgets:

- a 16-second retrieval and inference budget;
- two concurrent provider calls per process;
- a [circuit breaker](https://github.com/mrjithendar/roboshop-ai/blob/c81e85a1fd9d3552c69d4490be17ccf61d29437b/services/moks/README.md) that opens for 30 seconds after three failures.

Model output is guidance only. Moks has no database credentials and no tools that change carts or orders.

The [MCP server](https://github.com/mrjithendar/roboshop-ai/blob/c81e85a1fd9d3552c69d4490be17ccf61d29437b/services/mcp-server/README.md) is a separate entry point for AI clients. It takes the caller's own RoboShop session and forwards it to the gateway, which re-authorizes every call. Ten read tools and `update_cart` are registered by default, and admin write tools need an environment flag. Moks never calls MCP: the gateway already calls Moks, so that route would create a loop and add a hop without adding any authorization.

## How checkout and order events work

:::figure{caption="Figure 3. Money moves synchronously; fulfilment and analytics follow asynchronously."}
![Checkout and paid-order events. The browser creates an order at ai-gateway with an idempotency key; the gateway reserves stock in its ledger and calls payment-service and Razorpay, which can also send a signed webhook. Once paid, the ledger's outbox publishes to RabbitMQ: live orders go to shipping-service and PostgreSQL, with a dead-letter queue after five failures; test orders go to an audit queue; both go through kafka-bridge to Kafka.](/images/roboshop-ai/roboshop-ai-checkout-events.svg)
:::

Checkout is synchronous and deliberately conservative. The browser creates an order with an `Idempotency-Key`. The gateway snapshots the cart, reserves stock and records the order as `creating` before asking payment-service to create a Razorpay order, so two buyers cannot both pay for the last unit.

The server doesn't trust the browser's word that payment succeeded. It checks Razorpay's HMAC signature, then fetches the payment to confirm capture with the expected amount and currency. A signed webhook recovers callbacks the browser missed. If the provider's answer is unknown, the order moves to `payment_review` and keeps its reservation, rather than risking a second provider order. The [gateway README](https://github.com/mrjithendar/roboshop-ai/blob/c81e85a1fd9d3552c69d4490be17ccf61d29437b/services/ai-gateway/README.md#checkout-locking-and-recovery) documents the state machine.

The move to `paid` writes an `order.paid` event in the same ledger update, which is the [transactional outbox pattern](https://microservices.io/patterns/data/transactional-outbox.html). A background publisher sends it to RabbitMQ with [publisher confirms](https://www.rabbitmq.com/docs/confirms) and [quorum queues](https://www.rabbitmq.com/docs/quorum-queues).

Shipping inserts a shipment request before acknowledging, and unique event IDs make redelivery harmless. Five processing failures send a message to a dead-letter queue. Test-mode orders go to an audit queue and never create shipments. [kafka-bridge](https://github.com/mrjithendar/roboshop-ai/blob/c81e85a1fd9d3552c69d4490be17ccf61d29437b/services/kafka-bridge/README.md) copies both kinds to Kafka for analytics, and acknowledges RabbitMQ only after Kafka confirms.

Checkout never waits for shipping or Kafka. If RabbitMQ is down, events wait in the outbox.

## What the boundaries buy, and the conditions behind it

**Fault isolation.** This one has a live demonstration. On 2026-11-01 the assistant was missing from the cluster and chat returned 502, while the storefront and product API kept answering. That works because of explicit limits, not because of Kubernetes: a shared 23-second downstream budget, at most eight concurrent blocking handlers, and readiness that excludes optional features. Kubernetes restarts pods, but it does not make an application resilient. The gateway is still a single point of failure, and sessions fail closed when user-service is down.

**Independent deployment.** Each service has its own image, workflow and Argo CD Application. This depends on backward-compatible contracts, and rollback is weaker than it looks, because every image is a mutable `:latest`.

**Independent scaling.** This is mostly potential. Shipping supports multiple replicas, and currency-service keeps a per-replica cache. The gateway cannot scale, because its JSON ledger allows one writer, so it runs one replica with the `Recreate` strategy. A transactional PostgreSQL ledger exists but isn't the default. Every application runs one replica, and no autoscaler is defined for them. Scaling needs externalized state first.

**Languages suited to the task.** Go's standard library is enough for a small rate cache. Java fits the inherited shipping design. Python carries the AI libraries. You pay for each runtime in base images, dependency updates and expertise.

**Least privilege.** The Razorpay secret lives only in payment-service, SMTP credentials only in user-service, and Moks has no database access. Most application secrets still share one Kubernetes Secret, though, and MongoDB has one credential. Isolation comes from which keys each Deployment mounts.

**Identity between services.** On EKS, each workload has its own ServiceAccount, and so its own mesh identity. Policies describe the real call graph, with `allow-nothing` as the default. That benefit is prepared but not yet active: until mTLS is `STRICT` and policies leave dry run, nothing is denied.

**Testing through contracts.** The gateway has [user-service contract tests](https://github.com/mrjithendar/roboshop-ai/blob/c81e85a1fd9d3552c69d4490be17ccf61d29437b/services/ai-gateway/tests/test_user_service_contract.py), and NGINX tests run against a mock gateway. These are hand-written fixtures, so they protect only what someone remembered to assert.

**Reusing business APIs through agents.** MCP tools call the same gateway endpoints as the browser, so authorization stays in one place. Exposing MCP over the internet would also need OAuth 2.1, which is not implemented.

**Team ownership.** One person maintains everything, so this is something the design enables and does not demonstrate.

## What the boundaries cost

- **Latency and partial failure.** Each hop needs a timeout and a distinct failure outcome. A chat turn crosses the gateway, Moks, catalogue-service, a configuration check and a model.
- **Observability you must keep working.** Distributed tracing is designed in: NGINX, the gateway and MCP propagate [W3C Trace Context](https://www.w3.org/TR/trace-context/). On EKS the OpenTelemetry SDK is currently disabled, and the collector the services point at doesn't exist there. Without traces, you are reading separate logs and correlating by hand.
- **Coordinated changes.** Some changes need an order, such as upgrading Moks before the gateway. Argo CD doesn't prune old workloads either, so each consolidation needed manual clean-up.
- **Duplicates.** Delivery is at least once. Shipping deduplicates by event ID, and Kafka consumers must do the same.
- **No distributed transaction.** Checkout spans the ledger, Redis, Razorpay and user-service. Reservations, idempotency keys and reconciliation replace a transaction, and abandoned checkouts keep their reservations because nothing releases them automatically.
- **Operational weight.** There are eleven application images and CI workflows, plus Istio, Argo CD and secrets to manage.
- **Resource cost.** Kafka alone requests 768 MiB of memory. Two `t4g.large` nodes also have to carry a sidecar for every pod.
- **Distributed-monolith risk.** Every browser API call passes through the gateway, and catalogue reads a collection the gateway writes. If most changes touch several services at once, you have a monolith's coupling plus network costs.

Modernizing this system has sometimes meant fewer services, not more. Product ingestion and recommendations folded into catalogue-service, Finder and the shopping agent into Moks, and the frontend and NGINX into `web`.

## When a modular monolith would be simpler

For one team on one release cadence, a modular monolith is often the better start, which is the argument in Martin Fowler's [MonolithFirst](https://martinfowler.com/bliki/MonolithFirst.html). Catalogue, accounts, cart and checkout as modules in one process with one database would get in-process calls and ACID transactions for checkout. That removes most of the reservation and reconciliation machinery above.

RoboShop AI's gateway already behaves like a small modular monolith for checkout. Splitting further makes sense here only because the distributed operation is what's being practised. For a small shop, I would start with a monolith and extract a service only when a boundary proves itself.

## What to take from this

- Draw boundaries around data and rates of change, then accept that shared infrastructure blurs them.
- Keep authority in one place. Here the gateway owns stock and payment state, and everything else defers to it.
- Make optional features optional in readiness, routing and UI, not just in documentation.
- Design for at-least-once delivery from the first event.

Proposed next steps, none of them implemented yet: pin images by digest, move the gateway to the PostgreSQL ledger, give each service its own database credential, and restore tracing with durable storage.
