This site runs on a small self-managed Kubernetes cluster. Every release starts with a Git push and ends with a smoke test against the live site. Here is the whole path from `git push` to a page served over HTTPS.

## 1. Build a small, read-only image

Next.js can emit a self-contained server with `output: "standalone"`. The image copies only that output, which already includes the traced `node_modules` and the content files, and runs it as an unprivileged user:

```dockerfile
FROM node:26-alpine AS runtime
WORKDIR /app
ARG GIT_SHA=dev
ENV NODE_ENV=production HOSTNAME=0.0.0.0 PORT=3000 GIT_SHA=$GIT_SHA
COPY --from=build --chown=1000:1000 /app/.next/standalone ./
COPY --from=build --chown=1000:1000 /app/.next/static ./.next/static
USER 1000:1000
CMD ["node", "server.js"]
```

`GIT_SHA` is reported by a `/api/health` endpoint, which CI uses later to confirm which build is live.

## 2. Harden the pods

The Deployment runs two replicas with a read-only root filesystem, all Linux capabilities dropped and no service account token. Next.js writes its incremental static regeneration cache to disk, so that one path gets a writable `emptyDir`:

```yaml
securityContext:
  allowPrivilegeEscalation: false
  readOnlyRootFilesystem: true
  capabilities:
    drop: [ALL]
volumeMounts:
  - name: tmp
    mountPath: /tmp
  - name: next-cache
    mountPath: /app/.next/cache
```

A `preStop` sleep gives Traefik time to stop routing to a pod before it shuts down, so rolling updates do not drop requests.

## 3. HTTPS with cert-manager

A single `Certificate` covers the apex and `www` hostnames and is issued by a Let's Encrypt `ClusterIssuer`:

```yaml
apiVersion: cert-manager.io/v1
kind: Certificate
metadata:
  name: jithendar-com
spec:
  secretName: jithendar-com-tls
  dnsNames: [jithendar.com, www.jithendar.com]
  issuerRef:
    name: letsencrypt-prod
    kind: ClusterIssuer
```

## 4. Share one hostname with other apps

Other tools on the same hostname live under paths such as `/argocd` and `/grafana`. The site claims `/`, and Traefik gives longer rules priority by default, so the more specific routes keep working. Two small middlewares redirect `http` to `https` and `www` to the apex, each in a single hop.

## 5. Release from CI

The GitHub Actions workflow has three jobs:

1. **check**: lint, type check, tests, production build and a manifest render.
2. **publish**: builds an `arm64` image, pushes it to Amazon ECR, and commits the image **digest** into the production Kustomize overlay, so Git always records what is live.
3. **deploy**: runs `kubectl apply -k` against the overlay, waits for the rollout (and runs `kubectl rollout undo` if it fails), waits until `/api/health` reports the new commit, then smoke-tests the live site.

The deploy job authenticates as a dedicated ServiceAccount that can only manage the site's own resource types in its namespace. It cannot delete anything or read Secrets. Pinning by digest means the exact image that passed CI is the one that runs.
