If you are choosing between LangChain and LangGraph for an SRE agent, the first thing to know is that they are not really alternatives. LangChain's own agents [run on LangGraph](https://docs.langchain.com/oss/python/langchain/overview), and LangGraph [can be used without LangChain](https://docs.langchain.com/oss/python/langgraph/overview). The useful question is which parts you need.

This article answers it with one real codebase. MOKS is an SRE investigation portal I am building: an engineer asks a question, MOKS gathers live evidence through read-only tools, and returns a report that keeps facts, suspected causes and missing evidence apart. How MOKS uses the two frameworks is narrower than "built with LangChain and LangGraph":

- **LangGraph** runs the investigation. It owns the control flow, including the loop.
- **LangChain** appears only as `langchain-core`, for a chat model adapter, message classes and a tool wrapper. The `langchain` package is not installed.
- **Most of the agent is neither.** Permissions, budgets, tool validation, evidence, prompts and report checks are plain Python.

Native tool calling, checkpointing and `create_agent` are deliberately absent, and each absence is explained below. Code links point to [commit `9c150e9`](https://github.com/mrjithendar/moks/tree/9c150e99b8825c481430bdb9a2bf10df82756cb9) (1 November 2026); the last section notes what has changed since.

::toc

## Why MOKS needs a workflow, not one prompt

A single prompt cannot answer "why is this deployment restarting?" The answer is in live systems, and which ones to read depends on the last read. Order matters: a crash-looping container's current log is often empty during back-off, so MOKS reads logs [in every mode](https://github.com/mrjithendar/moks/blob/9c150e99b8825c481430bdb9a2bf10df82756cb9/backend/moks/orchestrator/engine.py) before any model is asked. The work must be bounded, must still produce a report when the model fails, and must cite evidence for every fact. That calls for a workflow where some steps are fixed, some are chosen by a model, and every exit is defined.

## Which parts of LangChain MOKS uses

LangChain's current docs centre on [`create_agent`](https://docs.langchain.com/oss/python/langchain/overview), which takes a model, tools and a system prompt and runs the model-and-tool loop for you, on LangGraph. MOKS pins only the lower layer, in [`backend/requirements.txt`](https://github.com/mrjithendar/moks/blob/9c150e99b8825c481430bdb9a2bf10df82756cb9/backend/requirements.txt):

```text
langchain-core==1.7.3
langgraph==1.2.19
```

`import langchain` fails in an environment built from that file, and a [test](https://github.com/mrjithendar/moks/blob/9c150e99b8825c481430bdb9a2bf10df82756cb9/backend/tests/test_investigation_graph.py) checks that vendor packages such as `langchain-openai` stay out.

| LangChain feature | In MOKS? | Detail |
| --- | --- | --- |
| `BaseChatModel` | Yes | Subclassed once, as `MoksChatModel` |
| `SystemMessage`, `HumanMessage`, `AIMessage` | Yes | Built for each model call |
| `StructuredTool` | Yes | Wraps planner tools around the policy path |
| `bind_tools`, `with_structured_output` | No | Both raise `NotImplementedError` on `MoksChatModel` |
| `ToolMessage` | No | Tool results return another way, covered below |
| `create_agent`, retrievers, prompt templates | No | Not installed or not imported |
| Vendor packages such as `langchain-openai` | No | Excluded on purpose |
| LangSmith tracing | No | Forced off |

### The chat model adapter

[`backend/moks/llm/lc.py`](https://github.com/mrjithendar/moks/blob/9c150e99b8825c481430bdb9a2bf10df82756cb9/backend/moks/llm/lc.py) implements `BaseChatModel` over MOKS's own LLM path:

```python
class MoksChatModel(BaseChatModel):
    ...
    def _generate(self, messages, stop=None, run_manager=None, **kwargs):
        raise NotImplementedError("MOKS is async: use ainvoke")

    async def _agenerate(self, messages, stop=None, run_manager=None, **kwargs):
        system = "\n\n".join(str(m.content) for m in messages if isinstance(m, SystemMessage))
        turns = [{"role": ROLES[m.type], "content": str(m.content)} for m in messages if m.type in ROLES]
        resp = await budget.complete(self.provider, system, turns, json_mode=self.json_mode, ...)
```

The [reference](https://reference.langchain.com/python/langchain-core/language_models/chat_models/BaseChatModel) lists `_generate` as required and `_agenerate` as optional; MOKS only calls asynchronously, so the sync path refuses. The call to `budget.complete` is why vendor packages are excluded: `langchain-openai` would talk to the provider directly, past budget reservations, daily limits and metering. So MOKS keeps its own [provider adapters](https://github.com/mrjithendar/moks/blob/9c150e99b8825c481430bdb9a2bf10df82756cb9/backend/moks/llm/providers.py) and puts the LangChain interface on top.

Importing this module also forces LangSmith tracing off (with `LANGSMITH_TRACING=true` set, `tracing_is_enabled()` returned `False`), because a trace would send prompts holding redacted evidence to a third party.

### The tool wrapper

[`backend/moks/tools/lc.py`](https://github.com/mrjithendar/moks/blob/9c150e99b8825c481430bdb9a2bf10df82756cb9/backend/moks/tools/lc.py) turns tool specs into `StructuredTool` objects:

```python
def wrap(spec: ToolSpec) -> StructuredTool:
    async def run(**args: Any) -> Any:
        purpose = args.pop("__purpose", None)
        return await call(spec.name, args, purpose)
    schema = spec.args.model_json_schema()
    schema["title"] = spec.name
    return StructuredTool.from_function(coroutine=run, name=spec.name, description=spec.description or spec.name, args_schema=schema)
```

[LangChain accepts](https://docs.langchain.com/oss/python/langchain/tools) a Pydantic model or a JSON Schema dict as `args_schema`. MOKS passes the dict on purpose: with a Pydantic schema, a bad call would fail inside LangChain and never reach the audit log or the rejected list the planner learns from. With a dict, the `ToolExecutor` stays the only validator. Honestly, this wrapper does very little; it is a uniform call interface around a function that already did the work.

### Why not native tool calling?

In LangChain's documented flow you [`bind_tools`](https://docs.langchain.com/oss/python/langchain/models), the model returns tool calls, and an agent runs them. MOKS lists tools as JSON in the prompt, and the model replies with one JSON object, as defined in [`prompts.py`](https://github.com/mrjithendar/moks/blob/9c150e99b8825c481430bdb9a2bf10df82756cb9/backend/moks/orchestrator/prompts.py):

```json
{"tool_calls": [{"tool": "<name>", "args": {}, "purpose": "<at most 12 words>"}], "done": false}
```

The [architecture notes](https://github.com/mrjithendar/moks/blob/9c150e99b8825c481430bdb9a2bf10df82756cb9/docs/ARCHITECTURE.md) give the reason: MOKS supports six provider types, and a JSON protocol behaves the same on all of them. The cost is that parsing, re-asking on malformed replies and schema enforcement are my code, not the provider's.

## What LangGraph does, shown through the MOKS graph

LangGraph is a [low-level orchestration framework and runtime](https://docs.langchain.com/oss/python/langgraph/overview): you define a graph of functions over shared state, and it runs them. The whole MOKS graph is 114 lines of [`backend/moks/orchestrator/graph.py`](https://github.com/mrjithendar/moks/blob/9c150e99b8825c481430bdb9a2bf10df82756cb9/backend/moks/orchestrator/graph.py), added in [commit `74cc81d`](https://github.com/mrjithendar/moks/commit/74cc81d) to replace a hand-written loop.

### State and nodes

[State](https://docs.langchain.com/oss/python/langgraph/graph-api) is a shared snapshot that nodes read and update:

```python
class State(TypedDict, total=False):
    namespace: str
    round: int
    calls: list[dict]
    use_rules: bool
    finished: bool
    report: Any
    mode: str
```

There is no `messages` list and no evidence. Graph state holds only what routing needs; the investigation lives on an `Investigator` object and in PostgreSQL. With no reducers, each update [overwrites its key](https://docs.langchain.com/oss/python/langgraph/graph-api). The eight nodes (`triage`, `logs`, `skills`, `plan`, `act`, `rules`, `correlate`, `report`) are thin calls into `Investigator`; as the docstring says, "The graph only decides what happens next."

### Edges, routing and the loop

These three lines are the agent's control flow:

```python
graph.add_conditional_edges("skills", lambda s: "plan" if provider else "rules", ["plan", "rules"])
graph.add_conditional_edges("plan", lambda s: "rules" if s.get("use_rules") else "act" if s.get("calls") else "correlate", ["rules", "act", "correlate"])
graph.add_conditional_edges("act", lambda s: "correlate" if s.get("finished") else "plan", ["plan", "correlate"])
```

The loop is `act` routing back to `plan`. Nothing in a graph makes a loop finite, so MOKS bounds it in `plan` with its own counters and sets a [recursion limit](https://docs.langchain.com/oss/python/langgraph/graph-api) as a backstop:

```python
limit = 2 * inv.settings.max_llm_rounds + 12  # every path is bounded; this only catches a mistake in the graph
return await compiled.ainvoke({"namespace": namespace}, {"recursion_limit": limit})
```

The limit counts super-steps, and LangGraph's default since 1.1.4 is 10,007, so a routing bug could run for a long time. With 4 rounds the MOKS limit is 20; the longest traced path ran 14 nodes.

### What MOKS does not use from LangGraph

| Feature | In MOKS? | What happens instead |
| --- | --- | --- |
| [Checkpointers](https://docs.langchain.com/oss/python/langgraph/persistence) | No, `compile()` takes none | Evidence is committed to PostgreSQL as it is collected |
| [Interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts) for human input | No | They need a checkpointer. Approval sits outside the graph, in action plans |
| [Streaming](https://docs.langchain.com/oss/python/langgraph/streaming) | No, the graph uses `ainvoke` | Nodes write events to a table, and an SSE endpoint polls it |
| Node retry policies | No | Provider adapters retry calls, and bad JSON gets one re-ask |
| Parallel branches | No | `act` runs tool calls one at a time |

Without a checkpointer, a dead worker's run is marked failed by a reaper after two minutes without a heartbeat. The evidence survives, but [the run cannot be resumed](https://github.com/mrjithendar/moks/blob/9c150e99b8825c481430bdb9a2bf10df82756cb9/docs/LIMITATIONS.md).

## LangChain vs LangGraph

| | LangChain | LangGraph |
| --- | --- | --- |
| **Main purpose** | Build LLM applications and agents quickly | Orchestrate long-running, stateful workflows |
| **Core abstractions** | Chat models, messages, tools, `create_agent`, middleware | State, nodes, edges, super-steps, checkpointers |
| **Control flow** | A ready-made model and tool loop that you customize | The flow you define, including loops and branches |
| **State and persistence** | Agent state, with persistence from the LangGraph runtime underneath | Explicit state schema, with optional checkpoints by thread |
| **Tool execution** | Defines tools; the agent loop runs them, or your code does | Runs whatever your node does, or a prebuilt tool node |
| **Appropriate use** | A standard agent, wide provider support, fast results | Mixed deterministic and model-driven steps, strict exits, custom recovery |
| **Role in MOKS** | `langchain-core` only: model adapter, messages, tool wrapper | The whole investigation control flow |

The docs recommend LangGraph for needs that [combine deterministic and agentic work](https://docs.langchain.com/oss/python/langchain/overview).

My rule for an SRE agent: if it is a model choosing tools until it finishes, start with `create_agent`. If the process has mandatory steps that run regardless of the model, plus defined fallbacks, write the graph. MOKS is the second case, because triage, logs and skills run before any model is consulted and a run must finish with no model at all. I have not built this on `create_agent` and middleware, so this is the reason for my choice, not proof that it could not work.

## The implementation, step by step

**Entry.** [`start_investigation`](https://github.com/mrjithendar/moks/blob/9c150e99b8825c481430bdb9a2bf10df82756cb9/backend/moks/api/investigations.py) applies rate and queue limits, resolves scope, checks RBAC and inserts a `queued` row. A [worker](https://github.com/mrjithendar/moks/blob/9c150e99b8825c481430bdb9a2bf10df82756cb9/backend/moks/orchestrator/worker.py) claims it with `FOR UPDATE SKIP LOCKED`, watches for cancellation and revoked access, re-checks authorization and calls `graph.run`.

**State lives in three places**, which is the main thing to understand about this design:

| Layer | Holds | Lifetime |
| --- | --- | --- |
| Graph `State` | Namespace, round, pending calls, routing flags, report | One run, in memory |
| `Investigator` object | Evidence, findings, notes, seen calls, rejected calls, token counts | One run, in memory |
| PostgreSQL | Events, evidence rows, audit, conversation messages, final report | Durable |

For a follow-up question, [`conversations.history`](https://github.com/mrjithendar/moks/blob/9c150e99b8825c481430bdb9a2bf10df82756cb9/backend/moks/conversations.py) loads up to 12 recent messages the person may still read, passed to the model as untrusted context.

**Models and tools are data.** One active `LLMConfig` row with purpose `chat` selects one of six adapters (`anthropic`, `openai`, `azure_openai`, `gemini`, `ollama`, `bedrock`); with none active, `provider` is `None` and the graph takes the rules path. Tools are 45 read-only `ToolSpec` entries in a [registry](https://github.com/mrjithendar/moks/blob/9c150e99b8825c481430bdb9a2bf10df82756cb9/backend/moks/tools/contracts.py), filtered per run by connectors and the requester's access.

**Choosing the next action.** After the fixed `triage`, `logs`, `skills`, `plan` makes one model call and sets state for the router. The model influences the path only through `tool_calls` and `done`:

```python
async def plan(state: State) -> dict:
    number = state.get("round", 0) + 1
    if number > inv.settings.max_llm_rounds or inv.tool_calls >= inv.settings.max_tool_calls:
        return {"calls": [], "finished": True}
    try:
        decided = await inv._plan_round(provider, cfg, inv._with_history(question), scope_info, number, ctx)
    except failures as exc:
        ...
        return {"use_rules": True}
    calls = decided.get("tool_calls") if isinstance(decided.get("tool_calls"), list) else []
    return {"round": number, "calls": calls, "finished": not calls or decided.get("done") is True}
```

**Returning tool results.** `act` runs up to four calls per round through `_call`, which skips exact repeats and enforces the tool budget, then through the [`ToolExecutor`](https://github.com/mrjithendar/moks/blob/9c150e99b8825c481430bdb9a2bf10df82756cb9/backend/moks/tools/executor.py); each result is redacted, truncated, stored and labelled (`E7`). There is no `ToolMessage` and no growing transcript: each round, `prompts.planner_user` rebuilds one user message from the question, scope, tools, remaining budget, findings, an evidence digest and rejected requests (13,566 and 14,003 characters in a traced run). Prompt size is capped at 3,500 characters per evidence item and 40,000 in total, but the model has no memory of its own earlier reasoning.

**Termination:**

| Condition | Enforced by | Result |
| --- | --- | --- |
| Model returns no calls or `done: true` | `plan`, `act` | Moves to `correlate` |
| A round produces no new call | `act` | Moves to `correlate` |
| 4 rounds used (`MOKS_MAX_LLM_ROUNDS`) | `plan` | Moves to `correlate` |
| Tool budget spent (`MOKS_MAX_TOOL_CALLS`) | `plan`, `_call` | Moves to `correlate` |
| Model error, or token budget of 60,000 | `plan`, `_check_budget` | Moves to `rules` |
| 180 seconds (`MOKS_MAX_DURATION_SECONDS`) | `asyncio.timeout` | Failed, with a partial report |
| Cancelled | Watcher | Cancelled, with a partial report |
| Access revoked | Guard and watcher | Stopped, with no report stored |
| Recursion limit | LangGraph | Failed as an internal error, with a partial report |

The tool-call default is 16 and the Helm chart [sets 24](https://github.com/mrjithendar/moks/blob/9c150e99b8825c481430bdb9a2bf10df82756cb9/deploy/helm/moks/values.yaml). Only the recursion limit is LangGraph's; every other bound is MOKS code.

**Evidence and uncertainty.** [`validate_llm_report`](https://github.com/mrjithendar/moks/blob/9c150e99b8825c481430bdb9a2bf10df82756cb9/backend/moks/orchestrator/report.py) checks the model's JSON report (the walkthrough below shows each rule firing), and `verify_causes` marks a cause verified only when a deterministic detector such as `oomkilled` or `crash_log_reason` observed the fault.

## Walking through one investigation

:::callout{type="warning" title="What this trace is, and is not"}
I ran this locally on 2026-11-01 at the commit above, with the real API, graph, `ToolExecutor`, detectors, skills and report validation on PostgreSQL 17. **The cluster is the repository's recorded `crashloop-invalid-config` fixture, and the model is a script.** It shows how MOKS handles a run, not its diagnostic quality, so I give no timings.
:::

The question: **"Why is the payments deployment repeatedly restarting?"**

**`triage`** produces evidence `E1` with findings including `crashloop` (pod `payments-5c4-z9`, 9 restarts) and `workload_unavailable`. **`logs`** reads pods, the pod description (`E3`), the previous container's log (`E4`) and the current one; exit code 78 adds a `crash_log_reason` finding quoting:

```text
{"level":"fatal","event":"config_invalid","message":"invalid PAYMENT_MODE=lve (expected live|sandbox)"}
```

**`skills`** selects two skills and records why:

```text
crashloop-triage   findings: crashloop; question: restarting
rollout-failures   findings: workload_unavailable; resource: Deployment
```

Their steps add rollout history, events and two empty `kb_search` results; repeats of `E3` and `E4` are skipped.

**`plan` and `act`, round 1.** The scripted model asks for four calls, one per outcome:

| Request | What happened |
| --- | --- |
| `k8s_events` in `moks-lab` | Exact repeat, skipped |
| `k8s_pod_logs` for the previous container | Exact repeat, skipped |
| `restart_deployment` | Rejected as `unknown_tool`, audited and added to the rejected list |
| `k8s_events` in `kube-system` | Ran and failed because the fixture has one namespace. Stored as failed evidence `E10` |

`restart_deployment` is not refused by a prompt; it is not in the registry at all. In round 2 the script asks for a repeat, `_act` counts zero new calls, and the loop exits on the "no new call" rule. **`correlate`** adds nothing, because the only rollout is older than the 60-minute window.

**`report`.** The script returns a deliberately bad report:

| The script sent | The stored report shows |
| --- | --- |
| A fact with no evidence, and one citing `E99` | Both dropped (`uncited_facts_dropped: 2`) |
| "Node pressure", confidence `high`, citing `E99` | Confidence `low`, citation removed |
| A summary saying the root cause "is confirmed" | "(Unverified: no change has been made or validated.)" appended |
| Remediation with `executable: true` | `executable: false`, `requires_approval: true` |
| "Invalid PAYMENT_MODE", `high`, citing `E3` | **Unchanged**, and still not verified |

The last row is a limitation: `E3` exists, so the citation passes, although the log line is in `E4`. Validation proves a reference is real, not that it supports the claim. Separately, `verified_causes` holds the `crash_log_reason` finding citing `E4`, and `crashloop-triage` suggested `rollback_deployment` and `open_pull_request`, neither of which runs anything.

The same fixture under other conditions:

| Run | Nodes after `skills` | Outcome |
| --- | --- | --- |
| No model | `rules`, `correlate`, `report` | Completed, `generated_by: rules` |
| Scripted model (above) | `plan`, `act`, `plan`, `act`, `correlate`, `report` | Completed, `generated_by: llm` |
| Provider down | `plan`, `rules`, `correlate`, `report` | Completed, rule-based, with notes saying so |
| Model never stops | 4 × (`plan`, `act`), `plan`, `correlate`, `report` | Completed. 5 model calls: 4 plans and the report |
| Model sends an argument named `self` | `plan`, `act`, then stops | **Failed**, see "Gaps" |

## RAG, skills, tools and the graph

These carry different trust. **RAG** answers "what did we write down?" from Git, uploads and postmortems, and is untrusted data. **Skills** (`SKILL.md`) answer "how should an SRE investigate this?" from the image or a reviewed ConfigMap, and are trusted instructions. **Tools** answer "what is true now?" from live systems, untrusted but policy-checked. **The graph** decides what happens next, in code.

Skills (51 built in) are [selected by plain rules](https://github.com/mrjithendar/moks/blob/9c150e99b8825c481430bdb9a2bf10df82756cb9/backend/moks/skills/__init__.py), run their steps in the `skills` node with or without a model, and add their body to the system prompt. [`kb_search`](https://github.com/mrjithendar/moks/blob/9c150e99b8825c481430bdb9a2bf10df82756cb9/backend/moks/tools/phase2.py) takes only `query` and `k`, so a model cannot widen its scope, and returns cited passages as ordinary evidence inside an `<untrusted_data>` block with a random tag. MOKS's RAG does not use LangChain retrievers; the [RAG and skills article](/blog/moks-rag-and-skills-design) covers it. To the graph, `skills` is just another node.

## Reliability and security

A graph makes control flow explicit; it will still loop forever or call anything you wire in. Every control below is ordinary code around the framework:

- **Tools** are read-only, and the `ToolExecutor` checks tool, arguments, RBAC and scope on every call and audits denials. The model has no shell or exec tool, and the chart's Kubernetes role has read verbs only, without Secrets, `pods/exec` or port-forward.
- **Scope** is RBAC intersected with environment allow and deny lists, re-checked before each tool and model call.
- **Limits:** 45 seconds per tool call, a per-provider timeout (default 60), 180 seconds per investigation, 4 rounds of up to 4 calls, 16 tool calls (24 in the chart), 60,000 tokens, plus daily budgets.
- **Failures degrade:** a failed tool becomes failed evidence, a missing connector a note, a model failure the rules path.
- **Data:** pattern-based redaction on evidence and prompts, random-tagged untrusted-data blocks, LangSmith off.
- **Changes:** a report only proposes. Plans go through separate approval, and only `moks-executor` holds write credentials.

### Gaps

Still present at MOKS `e66515a` (6 November 2026):

- **A malformed argument can fail the run.** An argument named `self` from a scripted model raised a `TypeError` inside LangChain's tool wrapper, before the `ToolExecutor`, and the investigation failed with a partial report. `_act` still has no per-call exception handling.
- **Arguments are not always untouched.** LangChain dropped keys named `config` and `run_manager` in my test, so they never reached the validator; LangChain [documents `config` as reserved](https://docs.langchain.com/oss/python/langchain/tools).
- **Citations are existence-checked only**, and **a stopped run cannot resume**.
- **The row's `mode` field** keeps its default of `llm` even for rule-based runs; the report's `generated_by` is correct.
- **Redaction is pattern-based**, so it [cannot recognize every secret](https://github.com/mrjithendar/moks/blob/9c150e99b8825c481430bdb9a2bf10df82756cb9/docs/LIMITATIONS.md), and redacted evidence still goes to the configured provider.
- **Prompt injection is contained, not prevented**: log text cannot add a tool or widen scope, but can mislead a suspected cause.
- **One shared Kubernetes identity** across users, so isolation relies on MOKS's checks; and a global administrator can [approve their own plans](https://github.com/mrjithendar/moks/blob/9c150e99b8825c481430bdb9a2bf10df82756cb9/docs/SECURITY.md), audited but alone.

Proposed, not built: reject reserved argument names and catch exceptions per call in `_act`; check that cited evidence relates to the claim; run the lab scenarios against a real model; and evaluate a checkpointer once real runs show whether resuming beats re-running.

## Lessons and trade-offs

**Easier:** routing is three lines, tested by asserting the compiled graph's nodes and edges, and "no model" or "planning failed" are edges, not branches buried in a loop. **Harder:** state lives in three places and nodes change `Investigator` directly, so adopting a checkpointer would need rework.

**What the frameworks did not do.** LangGraph supplies the recursion limit; everything else in the termination table is mine. The tool wrapper adds little that a dictionary of async functions would not, and `langchain-core` brought `langsmith`, which then had to be switched off. The JSON protocol gives identical behaviour across providers and one validator, at the price of provider-enforced schemas, a re-ask on bad JSON and the tool list resent every round.

**Since 1 November.** At `9c150e9`, no chat model had answered a live request in the lab. By 4 November one had: a trace on mk4 shows `gpt-6.1-sol` answering planning calls through the OpenAI-compatible adapter. The report still fell back to rules, because the investigation hit its 60,000-token budget (see [Observability for MOKS](/blog/moks-observability-logging-tracing-ai-agent-monitoring)). Skill selection also changed: a question keyword now scores 2 instead of 1. Whether MOKS is a good investigator with a real model is still unmeasured.
