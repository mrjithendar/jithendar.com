This site is built by GitHub Actions and runs on **mk4**, a k3s cluster on Hetzner Cloud that I manage myself: one control-plane node and three workers. GitHub's runners are throwaway machines somewhere on the internet, so every release has to answer one question: how does a throwaway virtual machine at GitHub prove to my cluster that it is allowed to touch the site?

This article walks through the exact answer used today, file by file, and then through its weak spots. All of it was checked against the live cluster on 3 November 2026, and updated on 14 November 2026: releases moved to their own image tags, the repository was renamed to `moks-cms`, and mk4 moved from minikube on one server to k3s on Hetzner Cloud (10 November 2026).

## 1. The short version

A release job on GitHub does four things to reach the cluster:

1. It builds a kubeconfig file at run time from a template in the repository and three values stored in GitHub.
2. It connects to the cluster's Kubernetes API over HTTPS, on port 6443 of the control-plane node.
3. It checks the server's certificate against the cluster's own certificate authority (CA), stored in GitHub as a variable.
4. It presents a bearer token that belongs to one ServiceAccount, `jithendar/github-ci-deployer`, which RBAC allows to do almost nothing.

Then it points every Deployment that runs the new image at the release's own tag with `kubectl set image`, waits with `kubectl rollout status`, and deletes the file.

```text
GitHub-hosted runner
  │  kubeconfig built from: MK4_API_SERVER (variable)
  │                         MK4_CA_DATA    (variable)
  │                         MK4_CI_TOKEN   (secret)
  ▼
https://<control-plane-ip>:6443     ← the Hetzner Cloud firewall allows 6443
  ▼
kube-apiserver (k3s, on jithendar-master1)
  ├─ TLS: certificate signed by the k3s server CA, SANs include the node's addresses
  ├─ Authentication: token → system:serviceaccount:jithendar:github-ci-deployer
  └─ Authorization: Role github-ci-deployer in namespace jithendar
```

## 2. Two systems, two kinds of credential

The same release job talks to two systems, and they authenticate differently.

| Target | How the job proves who it is | What is stored in GitHub |
|---|---|---|
| Harbor (image registry) | A Harbor robot account that may only push and pull in project `jithendar` | Its name and password, as repository secrets `HARBOR_USERNAME` and `HARBOR_PASSWORD` |
| mk4 (Kubernetes API) | A static ServiceAccount token | The token itself, as a repository secret |

Neither of them trusts GitHub's OIDC issuer, so both need a credential copied into the repository settings by hand. Until November 2026 images went to Amazon ECR instead, which does: the job exchanged a short-lived GitHub token for temporary AWS credentials, and only a role ARN was stored. That Terraform was removed once every release pushed to Harbor. Most of this article is about the second row.

## 3. Making the k3s API server reachable from the internet

![How GitHub Actions reaches the k3s API on mk4. A GitHub-hosted release job builds a kubeconfig at run time from the variables MK4_API_SERVER and MK4_CA_DATA and the secret MK4_CI_TOKEN, and connects over HTTPS on port 6443 through the Hetzner Cloud firewall, whose allowed_networks.api is 0.0.0.0/0 because runners have no fixed addresses. On the control-plane node jithendar-master1 the k3s API server presents a certificate from k3s-server-ca whose SANs are the node name and addresses, not jithendar.com, so CI connects by IP and verifies the CA. The bearer token maps to a ServiceAccount: github-ci-deployer may patch four Deployments, github-ci-applier may apply application objects, and neither may read Secrets or create pods. In namespace jithendar, scripts/ci-rollout.py runs kubectl set image to the pr-number tag for jithendar-com, the practice executor and the SEO agent, and deploy-kubernetes.yml applies the kubernetes folder on merge while keeping each Deployment's running image.](/images/mk4-k3s/mk4-k3s-ci-api.svg)

k3s runs the API server on the control-plane node, on port 6443, on every interface, so there is nothing to publish. Whether the internet can reach it is a firewall question. `hetzner-k3s`, the tool that created mk4, builds the Hetzner Cloud firewall from `allowed_networks` in its config (`hetzner-k3s.yaml` in my kubernetes repository):

```yaml
networking:
  allowed_networks:
    api:
      - 0.0.0.0/0   # tighten to your own IP
create_load_balancer_for_the_kubernetes_api: false
```

The API stays open to the whole internet because GitHub-hosted runners have no fixed addresses (section 9). With one control-plane node and no load balancer for the API, the server address in the kubeconfig is that node's public IP on port 6443.

The certificate is the other half. You can see it from any machine:

```bash
echo | openssl s_client -connect <control-plane-ip>:6443 2>/dev/null \
  | openssl x509 -noout -issuer -ext subjectAltName
```

```text
issuer=CN=k3s-server-ca@1794296796
X509v3 Subject Alternative Name:
    DNS:jithendar-master1, DNS:kubernetes, DNS:kubernetes.default, DNS:kubernetes.default.svc,
    DNS:kubernetes.default.svc.cluster.local, DNS:localhost, IP Address:<the node's addresses>
```

k3s signs the certificate with its own CA and lists the node's addresses, so `kubectl` can verify the server when it connects by IP. `jithendar.com` is not in the list and does not need to be: that name points at the Hetzner load balancer in front of the Istio gateway, not at the API. (To add a name, k3s takes `--tls-san`.) Without a matching name or address, the only way to connect would be `insecure-skip-tls-verify: true`, which lets anyone in the middle impersonate the cluster.

> Until 10 November 2026 mk4 was a minikube cluster on one server. Its API was published on a fixed host port with `--listen-address`, `--ports` and `--apiserver-names=jithendar.com`, and signed by `minikubeCA`. On k3s none of that is needed.

## 4. The identity: one ServiceAccount, one Role

The account CI uses is defined in `kubernetes/80-ci-deployer.yaml`. It has a ServiceAccount, a Role, a RoleBinding and a token Secret, all in namespace `jithendar`.

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: github-ci-deployer
  namespace: jithendar
---
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: github-ci-deployer
  namespace: jithendar
rules:
# kubectl rollout status
- apiGroups: ["apps"]
  resources: ["deployments", "replicasets"]
  verbs: ["get", "list", "watch"]
# kubectl set image, and kubectl rollout restart when a release is run again
- apiGroups: ["apps"]
  resources: ["deployments"]
  resourceNames: ["jithendar-com", "practice-executor-api", "practice-dispatcher", "seo-agent"]
  verbs: ["patch"]
- apiGroups: [""]
  resources: ["pods"]
  verbs: ["get", "list", "watch"]
```

Three details make this Role narrow:

- It is a **Role**, not a ClusterRole, so it grants nothing outside `jithendar`.
- `patch` is limited with `resourceNames` to four named Deployments: the site, the two practice executor Deployments and the SEO agent.
- There is no rule for `secrets`, no `create` and no `delete`.

`kubectl set image` and `kubectl rollout restart` both work with only `patch`, because neither deletes pods. `set image` changes the container image in the pod template, and `restart` writes a `kubectl.kubernetes.io/restartedAt` annotation into it; either way the Deployment controller replaces the pods. `rollout status` only needs to read Deployments and ReplicaSets.

You can check the result without the token, by impersonating the ServiceAccount as a cluster admin (with mk4's kubeconfig):

```bash
SA=system:serviceaccount:jithendar:github-ci-deployer
kubectl auth can-i patch deployment/jithendar-com -n jithendar --as=$SA   # yes
kubectl auth can-i patch deployment/moks-portal   -n jithendar --as=$SA   # no
kubectl auth can-i get secrets                    -n jithendar --as=$SA   # no
kubectl auth can-i create pods                    -n jithendar --as=$SA   # no
kubectl auth can-i get pods                       -n kube-system --as=$SA # no
```

Those are the answers mk4 gives today.

## 5. The token

A ServiceAccount has no password. Since Kubernetes 1.24, pods get short-lived tokens through the TokenRequest API, and no long-lived token is created automatically. CI runs outside the cluster and needs a token that survives between runs, so the manifest asks for an old-style one explicitly:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: github-ci-deployer-token
  namespace: jithendar
  annotations:
    kubernetes.io/service-account.name: github-ci-deployer
type: kubernetes.io/service-account-token
```

When this Secret is created, the token controller fills in `data.token` with a JWT signed by the cluster. The token has **no expiry**. It stays valid until the Secret (or the ServiceAccount) is deleted, which is also the way to revoke it.

The current token was issued on 10 November 2026, when the k3s cluster was set up, and has not been rotated since.

## 6. Getting the values into GitHub

`scripts/setup-ci-deployer.sh` is run once from my Mac, where `kubectl` has admin access to mk4 and `gh` is signed in. It does the whole setup:

1. Reads the API URL and CA certificate from the kubeconfig context it is given (`KUBE_CONTEXT`, mk4's).
2. Applies `kubernetes/80-ci-deployer.yaml` and waits for the token controller to fill in the token.
3. Builds a kubeconfig exactly as CI will, in a temporary file, and checks that it can patch `deployment/jithendar-com`.
4. Stores three values in the repository:

```bash
gh variable set MK4_API_SERVER --repo "$REPO" --body "$MK4_API_SERVER"
gh variable set MK4_CA_DATA    --repo "$REPO" --body "$MK4_CA_DATA"
printf '%s' "$MK4_CI_TOKEN" | gh secret set MK4_CI_TOKEN --repo "$REPO"
```

The token is piped through standard input, so it never appears in the terminal, the shell history or a process list. The temporary kubeconfig is deleted by a `trap` even if the script fails.

Why are two of the three values plain **variables**? The API URL and the CA certificate are not secret. The CA certificate is public by design: it lets a client verify the server, but it cannot be used to sign in. Only the token is a credential. Keeping the public values as variables makes them visible in logs and settings, which helps debugging, and keeps the secret list down to the one thing that must stay hidden.

`ROTATE=1 scripts/setup-ci-deployer.sh` deletes the token Secret first. The old token stops working immediately, a new one is issued and stored.

## 7. Building the kubeconfig in the job

The repository contains a kubeconfig **template**, `.github/jithendar-ci-deployer.yaml`, with placeholders instead of values:

```yaml
apiVersion: v1
kind: Config
clusters:
- name: mk4
  cluster:
    server: ${MK4_API_SERVER}
    certificate-authority-data: ${MK4_CA_DATA}
users:
- name: github-ci-deployer
  user:
    token: ${MK4_CI_TOKEN}
contexts:
- name: mk4
  context:
    cluster: mk4
    user: github-ci-deployer
    namespace: jithendar
current-context: mk4
```

The release job in `.github/workflows/ci-jithendar-com.yml` fills it in, uses it, and removes it (comments left out):

```yaml
- name: Roll out jithendar-com
  if: github.event_name != 'workflow_dispatch' || inputs.restart
  env:
    MK4_API_SERVER: ${{ vars.MK4_API_SERVER }}
    MK4_CA_DATA: ${{ vars.MK4_CA_DATA }}
    MK4_CI_TOKEN: ${{ secrets.MK4_CI_TOKEN }}
  run: |
    set -euo pipefail
    for v in MK4_API_SERVER MK4_CA_DATA MK4_CI_TOKEN; do
      [[ -n "${!v}" ]] || { echo "::error::$v is not set; run scripts/setup-ci-deployer.sh"; exit 1; }
    done
    export KUBECONFIG="$RUNNER_TEMP/kubeconfig"
    trap 'rm -f "$KUBECONFIG"' EXIT
    (umask 077; perl -pe 's/\$\{(MK4_[A-Z_]+)\}/$ENV{$1}/g' ../../.github/jithendar-ci-deployer.yaml > "$KUBECONFIG")
    python3 ../../scripts/ci-rollout.py "$REGISTRY_IMAGE" "$PR_TAG" --previous registry.jithendar.com/jithendar/jithendar-com
```

Line by line:

- **The `for` loop** fails fast with a clear message when a value is missing. Without it, an empty token would produce a confusing `Unauthorized` from the API server.
- **`$RUNNER_TEMP`** is a per-job directory that GitHub cleans up. The `trap` deletes the file earlier, when the step ends.
- **`umask 077`** makes the new file readable only by the runner user. It runs in a subshell `( … )` so it does not change the rest of the step.
- **The `perl` one-liner** replaces only placeholders that look like `${MK4_…}` with the matching environment variable. It does the same job as `envsubst`, but it cannot touch any other `$` in the file. The setup script uses the identical command, so what it tested locally is what CI builds.
- **`ci-rollout.py`** finds every Deployment in the namespace that runs a container from `$REGISTRY_IMAGE`, sets it to `:pr-<number>` and waits for each rollout. `--previous` also matches the image's old name, `jithendar-com`, so the first release after the rename still found the site.
- **The secret only enters this one step**, through `env:`. Other steps never see it, and GitHub masks its value in the log.

The practice executor and SEO agent workflows (`ci-practice-executor.yml`, `ci-seo-agent.yml`) sign in the same way, with the same three values, and run the same `ci-rollout.py` for their own images. That is why the Role names their Deployments too.

## 8. A catch: authenticated is not the same as deployed

Authentication worked from the start. The release on 2 November logged:

```text
deployment.apps/jithendar-com restarted
deployment "jithendar-com" successfully rolled out
```

and the site went on serving an older commit. The restart was designed for a Deployment that ran `jithendar-com:latest` with `imagePullPolicy: Always`, so new pods would pull whatever `:latest` pointed to. By then the site was no longer deployed that way: a separate `./deploy.sh` pinned an exact image digest in the kustomization and applied it, and the live Deployment ran:

```text
jithendar-com@sha256:ab475be7…   (commit a153283)
```

while `:latest` in the registry pointed to commit `dc249e8`. A restart re-creates pods from the same pod template, so they pulled the pinned digest again. CI reported success, and the site kept serving `a153283`, which is exactly what `/api/health` returned.

The fix (14 November 2026) used a permission the Role already had: CI now sets the image instead of only restarting. Each release pushes the image under the pull request's own tag, `moks-cms:pr-<number>` (the image was renamed from `jithendar-com` along with the repository), and `scripts/ci-rollout.py` points every Deployment that runs that image at the new tag with `kubectl set image`, which is a `patch` like `restart`. Only a Deployment that is already on that tag, because the job was run again, is restarted. `deploy.sh` is gone: `deploy-kubernetes.yml` applies manifest changes and keeps the image each Deployment is running, so applying manifests never rolls the site back. The Deployment now records which release is live:

```bash
kubectl -n jithendar get deploy jithendar-com -o wide
```

and going back is `kubectl -n jithendar set image deploy/jithendar-com web=<registry>/moks-cms:pr-<earlier number>`.

The general lesson: a green `rollout status` only proves the pods are ready. To prove the right code is running, check the version the app reports, as the smoke test before the push already does.

## 9. Security boundaries and weak spots

This setup is deliberately small, but it has real limits.

**The Kubernetes API is open to the internet.** GitHub-hosted runners do not have fixed IP addresses, so the port cannot be limited to them with a simple firewall rule. Anyone can reach the API and read its version (`/version` is public by default); everything else needs a valid token. The cluster's safety rests on the token staying secret and on the API server staying patched.

**The token never expires.** If it leaks, it works until someone runs `ROTATE=1 scripts/setup-ci-deployer.sh`. There is no automatic rotation.

**`patch` on a Deployment is more than restart.** The Role cannot read Secrets or create pods directly, but whoever can patch `deployment/jithendar-com` can change its image or its pod template. The Deployment controller would then run that code with every Secret the site's pods already receive, such as the database URL. The namespace has no Pod Security labels. Gatekeeper refuses privileged pods, host namespaces and hostPath volumes across the cluster, but its webhook fails open, and nothing stops a patched Deployment from running a different image with the site's Secrets. Treat this token as close to "can run code as the website".

**The secret is repository-wide.** `MK4_CI_TOKEN` is a repository secret, so a workflow running on any branch pushed to this repository can read it. The `if:` on the release job does not protect it; a changed workflow file on another branch could print or use it. Forks do not get repository secrets. The Harbor robot's password is a repository secret too.

**Comments have drifted.** The header of `kubernetes/80-ci-deployer.yaml` still says CI restarts the site after pushing a new `:latest` image, and the kubeconfig template says a step called "Restart jithendar-com" fills it in "with envsubst". Neither is true any more.

## 10. What I would change next

In order of effort:

1. **Move `MK4_CI_TOKEN` into a GitHub environment** restricted to the default branch. Then only jobs that declare that environment can read the token.
2. **Rotate the token on a schedule** with `ROTATE=1`, and after any change of who has write access to the repository.
3. **Add Pod Security `restricted` labels** to the `jithendar` namespace, as a second layer behind Gatekeeper, whose webhook fails open.
4. **Drop the static token entirely.** Kubernetes can be configured to accept JWTs from an external OIDC issuer with the API server's structured authentication configuration. With GitHub's issuer trusted, a job would sign in with the short-lived OIDC token GitHub can issue to every job, and the `sub` claim could be limited to this repository's default branch. On k3s that means passing an authentication config file to the API server (`--kube-apiserver-arg`), which I have not tried on mk4.

## 11. Recap

- The cluster is reachable because k3s serves the API on port 6443 of the control-plane node, the Hetzner Cloud firewall lets it through, and the certificate lists the node's address.
- CI trusts the server through the CA certificate (`MK4_CA_DATA`), not by skipping TLS checks.
- The server trusts CI through a long-lived ServiceAccount token (`MK4_CI_TOKEN`), the only real secret.
- RBAC limits that token to a few named objects in one namespace; `kubectl auth can-i --as` proves it.
- The kubeconfig exists only for one step: built from a template, readable only by the runner user, deleted on exit.
- Authentication is not deployment: check the version that is actually running.

### Checklist

- [ ] Open the API port (6443 on k3s) in the cloud firewall, and connect by a name or address that is in the API server's certificate (`--tls-san` adds one).
- [ ] Create a ServiceAccount with a namespaced Role; limit `patch` with `resourceNames`; grant no Secrets.
- [ ] Verify the Role with `kubectl auth can-i --as=system:serviceaccount:<ns>:<name>`.
- [ ] Request a token with a `kubernetes.io/service-account-token` Secret; know that it does not expire.
- [ ] Store the API URL and CA as variables and only the token as a secret; pipe the token into `gh secret set`.
- [ ] Build the kubeconfig in the job with `umask 077`, delete it with a `trap`.
- [ ] Never use `insecure-skip-tls-verify`.
- [ ] Prefer an environment-scoped secret, and plan for short-lived OIDC tokens.
