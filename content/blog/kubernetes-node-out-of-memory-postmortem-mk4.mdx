On 28 November 2026, one worker node of mk4, the k3s cluster that runs jithendar.com, stopped responding for almost eleven minutes. Argo CD, Grafana, Prometheus, Open WebUI, docling and the LiteLLM proxy went down with it, and Harbor, the image registry, followed a minute later because the Valkey instance it depends on was stuck on the same node. The blog itself kept answering: its pods happened to be on the other two workers.

It was my fault. I ran `kubectl rollout restart` on a Deployment whose previous rollout had only just finished, on a node that already had 91% of its memory in use. The scheduler put the new pod on that same node because, by its accounting, there was plenty of room. There wasn't. This is what happened, how the cluster recovered step by step, why nothing stopped it, and what I am changing.

## What I was doing that morning

I was moving the cluster's LiteLLM proxy (the OpenAI-compatible gateway in front of Claude, in namespace `rag`) onto PostgreSQL, so that models and keys could be managed from its admin UI. That change also raised LiteLLM's memory request from 384 MiB to 1 GiB and its limit from 1.5 GiB to 2 GiB, because I had measured it at 1.16 GiB without a database.

The new pod was scheduled at 10:56:19 and then waited ten minutes for three new keys in its Secret, which I had not created yet. Once I added them, it started at 11:06:36 on worker1, ran its database migrations, and was serving by 11:07:33. The old LiteLLM pod, on worker2, went away.

Then I noticed that one of the keys, the admin user name, had been saved empty (the shell I pasted the command into did not prompt for it). I fixed the value in the Secret and, because LiteLLM reads its environment only at start-up, ran:

```bash
kubectl rollout restart deploy/litellm
```

That was the mistake. Not the restart itself, but where it put the new pod and when.

### 1. Notice

At about 11:20 a log stream in k9s for the new LiteLLM pod kept failing with `proxy error … while dialing <worker1>:10250, code 502`: the API server could not reach worker1's kubelet. One command showed why:

```bash
kubectl get nodes
# jithendar-pool-workers-worker1   NotReady
```

### 2. Size the damage

Before touching anything I wanted to know what was down and what was not:

```bash
curl -s -o /dev/null -w '%{http_code}\n' https://jithendar.com/                      # 200
kubectl -n istio-ingress get pods -o wide                                            # one of two replicas on worker3
kubectl get pods -A -o wide --field-selector spec.nodeName=jithendar-pool-workers-worker1
```

The site was up, and the gateway still had a healthy replica on worker3. The list of pods on worker1 was long: most of the admin tools, Valkey's `valkey-0`, docling, Open WebUI and the new LiteLLM pods.

### 3. Do no more harm

The cluster was in the middle of evicting pods from an unreachable node, and the other workers were already short of requested memory. Every action I could take (another restart, deleting the stuck pods, scaling something up) would add load or another pod start. A pod start was exactly what had caused this. So I did none of them.

### 4. Look at the node from outside

The node's conditions had been `Unknown` since its last heartbeat:

```bash
kubectl get node jithendar-pool-workers-worker1 \
  -o jsonpath='{range .status.conditions[*]}{.type}={.status} {.lastHeartbeatTime}{"\n"}{end}'
# Ready=Unknown 2026-11-28T11:10:22Z  (and the same for MemoryPressure, DiskPressure, PIDPressure)
```

By the time I was looking, it was coming back: at 11:21:16, eleven seconds after it reported Ready again, metrics-server read its CPU at 3.9 of 4 cores. A node that is alive but spends all its CPU getting nowhere looks like memory thrashing. The events said the rest:

```bash
kubectl get events -A --field-selector involvedObject.kind=Node --sort-by=.lastTimestamp
kubectl get events -A --field-selector reason=SystemOOM
# SystemOOM  node/jithendar-pool-workers-worker1  System OOM encountered, victim process: docling-serve
```

If it had not come back, the next step would have been a reboot from the Hetzner console. I had no shell on the node, and the Hetzner CLI on my laptop had no context configured, so that would have been slower than it should be.

### 5. The node comes back

At 11:20:54 the kernel's OOM killer finally killed a process: docling-serve, the biggest pod on the node at 1.73 GiB. That freed enough memory for the kubelet and the k3s agent to work again: the node reported Ready at 11:21:05. The kubelet then stopped the pods that had been marked for deletion at 11:18:11, and the node controller cancelled the deletions it had not started.

### 6. Dependents recover

Harbor was the slowest. Its core had given up at 11:21:11 (`failed to initialize cache: retry timeout: EOF`) and was in crash-loop back-off. Once `valkey-0` was recreated at 11:22:03, the next restart of Harbor core at 11:23:52 came up cleanly, image pulls from registry.jithendar.com worked again, and the pods waiting on images started. At 11:25:47 nothing in the cluster was in any state other than Running or Completed:

```bash
kubectl get pods -A --no-headers | awk '$4!="Running" && $4!="Completed"'   # empty
```

### 7. Confirm the cause

With everything back, I collected what would expire first (events last an hour on k3s) and checked the story against it:

```bash
kubectl get events -A -o json > events.json
kubectl -n rag get rs -l app=litellm -o custom-columns=NAME:.metadata.name,CREATED:.metadata.creationTimestamp
# litellm-68dcddb4dd   2026-11-28T11:10:23Z   <- the ReplicaSet my restart created, one second after the last heartbeat
kubectl get --raw /api/v1/nodes/jithendar-pool-workers-worker1/proxy/configz \
  | jq '.kubeletconfig | {evictionHard, systemReserved, kubeReserved}'
```

And in Prometheus, worker1's memory before the gap:

```promql
container_memory_working_set_bytes{id="/", node="jithendar-pool-workers-worker1"}
# 11:06:12  6.05 GiB
# 11:07:13  6.86 GiB   <- LiteLLM 1 has started
```

## Root cause

### The arithmetic

worker1 has 7.55 GiB. At 11:10:15, 6.88 GiB of it was in use, 1.02 GiB of that by the first LiteLLM pod. The second LiteLLM pod needed about as much again to start: it imports a large Python application and runs the Prisma CLI for its migrations. 6.88 + 1.05 is about 7.9 GiB on a machine with 7.55. Something had to give, and nothing was set up to give gracefully.

### Why the scheduler said yes

The scheduler does not look at memory in use. It adds up memory **requests**, the amount each pod asks for, and compares that with the node's allocatable memory. On worker1 at 10:25, pods requested 5.28 GiB (69%) but used 6.1 GiB (80%). Many of the cluster's workloads ask for less than they use (worker1's pods' limits added up to 267% of the node). Two LiteLLM pods at 1 GiB each took the requested total to about 7.3 GiB: under 7.55, so it fits.

worker1 was also the node with the most unrequested memory, which is why the scheduler preferred it, twice. It was, at the same time, the node with the least real headroom. Ten minutes later the same accounting worked the other way: the replacements for worker1's pods could not be placed on worker2 or worker3 ("Insufficient memory"), because by requests those were full. The cluster has no spare node's worth of capacity.

### Why the kubelet didn't evict anything

The kubelet can evict pods before a node runs out of memory, if it has a memory threshold. mk4's kubelets have only disk thresholds:

```json
{
  "evictionHard": { "imagefs.available": "5%", "nodefs.available": "5%" },
  "systemReserved": null,
  "kubeReserved": null
}
```

That is the same on all four nodes. With no `memory.available` threshold the kubelet never evicts for memory, and with nothing reserved, allocatable memory is the whole machine: the scheduler can promise every byte to pods and leave nothing for the kernel, the kubelet, the k3s agent and containerd.

### Why it took ten minutes

This part is my reading, not something I measured on the node. When memory runs out, the kernel first reclaims what it can: page cache, including the pages of the programs that are running. Programs then have to read their own code back from disk, the next one evicts it again, and everything slows to a crawl. That is thrashing, and it fits a node at full CPU that answers nothing. The kubelet and the k3s agent were starved too, which is why heartbeats and probes stopped. The OOM killer only acts when reclaim fails outright, which here took about ten minutes. Then it picked the biggest process, docling-serve.

### The near miss I walked past

At 10:23 the same morning I had run a command (`prisma --version`) inside the old LiteLLM container to check its version. The container was using about 1.2 GiB of its 1.5 GiB limit, the extra process pushed it over, and it was killed with exit code 137; it came back within a minute. That was the same lesson at container scale: LiteLLM sits close to its memory, and starting one more thing next to it is enough. I raised its limit and moved on, without looking at the node it would land on.

## What went well, and what didn't

**Went well:**

- **The blog stayed up.** Both site replicas were on nodes other than worker1, and the ingress gateway had a second replica on worker3.
- **The node recovered without a reboot,** and I found nothing lost: Valkey came back with its data, PostgreSQL was never on worker1, and no volume was damaged.
- **I didn't make it worse.** No second restart, no force-deleted pods, no rescheduling by hand while the cluster was already short of room.
- **The evidence was collected before it expired.** Events, memory samples and the kubelet's configuration were saved within half an hour.

**Didn't go well:**

- **A person found it, by chance.** No rule watches node readiness or node memory, mk4 has no Alertmanager, and Prometheus itself ran on the node that failed, so it could not have alerted anyway.
- **I restarted without looking.** One `kubectl top nodes` would have shown worker1 at 91%.
- **Requests that understate use** let the scheduler place a 1 GiB pod on a node with 0.67 GiB free.
- **One node carried too much that others depend on:** Valkey's `valkey-0`, Prometheus, Grafana, Argo CD and Open WebUI, several with volumes pinned to it.
- **I had no quick way into the node:** no shell, and no Hetzner CLI context for a reboot.

## Key takeaways

1. **The scheduler counts requests, not memory in use.** If requests are low, "it fits" means nothing. Check `kubectl top nodes` before you add a pod by hand.
2. **A node with no memory eviction threshold and nothing reserved will thrash, not evict.** Kubernetes protects a node from memory pressure only if you tell the kubelet where the line is.
3. **`kubectl rollout restart` starts a new pod before it stops the old one.** On a tight cluster, that extra pod is the risk, and a rollout that has just finished is the worst moment for it.
4. **Your monitoring has to live somewhere else.** A Prometheus on the failing node sees nothing at the moment it matters.
5. **When a node is unreachable, stop changing things.** Size the damage, look from outside, and let the cluster settle before you act. Here, waiting was the recovery.
